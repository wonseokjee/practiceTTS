# 화자 개인화 설계 — 쓸수록 알아듣게 만들기

- **작성일**: 2026-08-19
- **개정**: 2026-08-20 — 미해결 5건 중 4건 결정(결정 3 개정, 결정 6~8 추가)
- **주제**: 환자 개인의 발화로 ASR을 적응시켜(3~4층) 연습·대화 모드 인식률을 올린다
- **상태**: **미착수(설계)**. 선행 조건은 2층(608 도메인 적응) 안정화 + **음향 채점기** — [파인튜닝 대장](608-finetune-log.md) 참조
- **성격**: 착수 시점에 다시 유도하지 않기 위한 결정 기록. 수치는 여기에 적지 않는다

## 왜 이 문서인가

"환자가 쓰면 쓸수록 잘 알아듣게 되는가"는 답이 **"된다, 그러나 그냥 켜면
제품이 망가진다"** 이다. 망가지는 방식이 조용해서(정확도가 올라가는 것처럼
보인다) 착수할 때 반드시 이 문서를 먼저 봐야 한다.

## 1. 층 모델과 현재 위치

구음장애 ASR에서 가장 큰 레버는 더 큰 모델도 더 많은 데이터도 아니고 **한 사람에게
맞추는 것**이다. 왜곡이 개인 사이에선 제각각인데 **개인 안에서는 일관적**이기
때문이다. 배경은 [`docs/learning/dysarthria-agent/05-speaker-adaptation.md`](../learning/dysarthria-agent/05-speaker-adaptation.md).

| 층 | 내용 | 필요 데이터 | 우리 상태 |
|---|---|---|---|
| 1층 | 사전학습 모델 | 수만 시간 | whisper large-v3-turbo 사용 중 |
| 2층 | 구음장애 전반 적응 | 수십~수백 시간 | **진행 중** (608, 7차까지) |
| 3층 | 이 환자에게 개인화 | **수분~수십 분** | 미구현 (`adapters.FinetuneAdapter`는 스캐폴드) |
| 4층 | 쓰면서 계속 갱신 | 사용 중 누적 | 미착수 — 이 문서의 주제 |

**3층의 데이터량이 작다는 것이 이 접근이 현실적인 근거다.** 환자에게 30분은
요구할 수 있어도 10시간은 요구할 수 없다.

**순서를 지킬 것.** 개인화는 공통 모델 위에 얹는 얇은 층이라, 밑(2층)이 흔들리면
환자별 조각을 전부 다시 학습해야 한다. 2층이 안정되기 전에 3층을 시작하지 않는다.

## 2. 이미 깔려 있는 기반

빈칸은 사실상 **학습 루프 하나**다.

| 조각 | 위치 | 상태 |
|---|---|---|
| 발화 보존(동의 기반) | `backend/src/speech-data/entities/speech-recording.entity.ts` | 있음 |
| 화자별 분리 저장 | 같은 파일 (`audio_path = <patientId>/<uuid>.wav`) | 있음 — 삭제 요구 시 조각만 제거 |
| 라벨 후보 + 가설 + 점수 | `target_text` / `recognized_text` / `score` | 있음 |
| 라벨 품질 필터 export | `scripts/asr_eval/build_training_set.py` | 있음 |
| 어댑터 인터페이스 | `scripts/asr_eval/adapters.py` (`Adapter` 프로토콜) | 있음 |
| 화자별 학습 루프 | `FinetuneAdapter` | **없음(스캐폴드)** |
| 서빙 시 조각 로딩 | `ai-service/interfaces/stt_engine.py` 구현체 | **없음** |

환자별 LoRA 어댑터는 수십 MB다. **공통 모델 하나 + 환자별 조각** 구조가 저장·배포
모두 감당 가능하다.

## 3. 근본 긴장 — 인식과 측정은 목적이 충돌한다

**이 문서에서 하나만 가져간다면 이 절이다.**

앱은 두 가지를 동시에 원한다.

| 원하는 것 | 어디서 | 개인화의 효과 |
|---|---|---|
| 환자 말을 **알아듣기** | 대화 모드(`TrainingScreen`), 연습 모드 | 좋아진다 |
| 환자 발음이 **정확한지 재기** | QAB 검사(naming/repeat/reading), 주간 리포트 | **망가진다** |

개인화된 모델은 그 환자의 **틀린 발음도 정답으로 알아듣는다.** 그것이 개인화의
정의다. 그러면 이런 경로가 열린다.

```
환자가 /바다/를 /파다/로 발음
  → 개인화 ASR이 "바다"로 전사 (개인화가 잘 된 것)
  → isNameMatch 통과 → qabResults에 정답으로 기록
  → WeeklyReportScreen의 회복 추세 상승
  → 그런데 환자는 회복하지 않았다. 모델이 적응했을 뿐이다.
```

재활 도구에서 **잣대가 환자를 따라 움직이면 측정 기능이 죽는다.** 이 앱의 존재
이유가 회복 추세를 보여주는 것이므로 이건 부작용이 아니라 제품 파괴다.

### 결정 1 — 개인화 모델과 채점 잣대를 격리한다

| 기능 | 쓰는 것 |
|---|---|
| 대화 모드 · 연습 모드 인식 | **개인화 ASR** (알아듣는 것이 목적) |
| QAB 검사 채점 | **개인화하지 않은 고정 잣대** — 음향 기반 발음 점수 |

같은 모델을 양쪽에 쓰지 않는다. 이 경계가 무너지면 위 시나리오가 조용히 발생한다.

### 결정 6 — 개인화 전사는 채점 경로에 넣지 않는다 (그래서 음향 채점기가 선행이다)

"인식은 개인화하되 **점수만** 고정 잣대로" 라는 절충이 가능한지 물었고, 답은
**조건부로 가능**이다. 조건이 하나뿐이라 분명하다.

> **전사 기반 채점에서는 불가능하다.** `isNameMatch`·`evaluateSpeech`는 전사
> 텍스트를 입력으로 받는다. 개인화 전사를 넣는 순간 인식과 점수가 같은 값을
> 공유하므로 점수도 같이 오염된다.

성립하는 유일한 형태는 **채점이 음향에서 직접 나올 때**다.

```
개인화 ASR ──→ 전사 ──→ 대화·연습·"이렇게 들었어요" 표시·재시도 유도
공통 모델  ──→ 음향 점수 ──→ QAB 점수   (전사를 거치지 않는다)
```

앱은 이미 이 구조에 가깝다. `PictureNamingItem`은 Azure 발음평가(`accuracyScore`,
음소 단위)를 1순위로 쓴다. **오염 경로는 딱 하나 — Azure 실패 시의 문자열 폴백**이다.

- 개인화 전사는 채점 함수에 **절대** 전달하지 않는다. 쓰이는 곳은 (i) 대화 모드,
  (ii) "이렇게 들었어요" 표시, (iii) 재시도 유도뿐이다
- Azure 실패 시 개인화 전사로 폴백 채점하지 않는다. 공통 모델 전사로 채점하거나
  그 문항을 **채점 불가**로 남긴다

이 결정의 대가는 명확하다. **Azure 발음평가 의존이 영구화된다.** 벗어나려면 자체
음향 채점기(forced alignment + GOP 계열)가 필요하고, 그 채점기는 반드시
**개인화 조각을 끼지 않은 공통 모델**로 돌려야 한다.

> **채택된 순서: 음향 채점기가 3층보다 먼저다.** 개인화를 켜는 순간 폴백 경로가
> 위험해지므로, 고정 잣대를 자체적으로 확보하기 전에는 개인화를 서빙에 올리지
> 않는다. 개인화 착수가 그만큼 늦어지는 것을 감수한다.

## 4. 라벨 문제 — `target_text`는 라벨이 아니다

엔티티 주석이 이미 경고하고 있다: "환자는 목표와 다르게 발화할 수 있어 그 자체로는
신뢰 라벨이 아니다."

제시한 텍스트를 그대로 정답으로 학습시키면 모델은 **"이 환자의 /파다/는 바다다"**
를 배운다. 3절의 붕괴가 학습 단계에서부터 시작되는 셈이다.

### 결정 2 — 라벨 신뢰 게이트를 통과한 발화만 학습에 넣는다

`target_text`와 `recognized_text`의 근접도, `score`를 함께 본다. 게이트 설계는
착수 시 정하되 원칙은 이렇다.

- **일치도가 높은 것만** 학습에 넣는다(목표대로 말한 것으로 간주)
- **점수가 낮은 것은 제외**한다 — 틀리게 발음한 것을 정답에 매핑하지 않는다
- 게이트 임계값은 앱의 정답 경계(0.34)보다 **엄격**해야 한다. 채점 통과와 학습
  적격은 다른 기준이다

## 5. 확증 편향 루프 — 커브가 일찍 평평해진다

```
잘 알아들은 발화만 게이트 통과 → 학습에 포함
못 알아들은 발화는 게이트 탈락 → 영원히 학습에서 빠짐
→ 모델은 이미 잘하는 것만 더 잘하게 된다
```

4절의 게이트가 5절의 편향을 만든다. 둘은 같은 장치의 양면이라 게이트만 넣고
끝내면 안 된다.

### 결정 3 — 탈락 발화는 보호자가 **전사**하지 않고 **판정**한다

보호자는 사실 최적의 라벨러다. 가족은 낯선 사람보다 환자 말을 훨씬 잘 알아듣는다.
문제는 능력이 아니라 **부담**이고, 이 앱은 보호자가 이미 지쳐 있다는 전제 위에
서 있다. 그러므로 자유 전사(타이핑)는 답이 아니다.

```
어제 이렇게 말씀하셨어요  🔊 ▶
목표는 "바다" 였어요. 맞게 들리시나요?
[ 맞아요 ]  [ 아니에요 ]  [ 잘 모르겠어요 ]
```

**1탭이다.** "맞아요"면 `target_text`가 라벨로 승격돼 게이트를 우회한다. 자유
전사는 최후 수단으로만 남긴다. 설계 제약 세 가지:

- **관찰 도구로 프레이밍한다.** 할 일이 아니라 "환자가 오늘 뭐라고 말했는지 듣는 창"
- **연타 방지.** 하루 N개 제한, 확인 라벨은 별도 신뢰도 태그로 저장
- **"잘 모르겠어요"를 눈에 띄게.** 중립 선택지가 없으면 사람은 긍정을 누른다

미결로 남은 것은 방식이 아니라 **이 화면을 만들 것인가**다(10절).

## 6. 데이터 속도 — 반년이 걸린다

앱의 단어 클립은 0.3~1.5초(중앙값 0.58초)다. 3층에 쓸 10~30분을 단어만으로 모으려면
**1,000~3,000발화**가 필요하고, 하루 20문항이면 **반년**이다.

### 결정 4 — 연습 모드를 데이터 엔진으로 본다

```
검사 문항 (느림, 라벨 확실)  ─┐
연습 모드 (빠름, 라벨 확실)  ─┼→ 환자별 LoRA 조각 → 대화 모드 인식에만 적용
대화 모드 (라벨 없음)        ─┘
```

연습 모드는 판정을 환자에게 보이지 않으므로(설계상) 부담 없이 많이 말하고, 목표
텍스트가 있어 라벨이 붙는다. **개인화의 데이터 공급은 연습 모드가 감당한다.**

### 결정 5 — 적응 데이터는 분산해서 모은다

한 세션에 30분을 몰아 받는 것보다 **여러 날에 나눠** 받은 데이터가 견고하다. 병리
발화는 컨디션에 따라 변동이 크고, 구음장애 환자에게 말하기는 체력 소모다. 앱의
일일 사용 패턴이 이미 이 조건을 만족한다 — 별도 등록 절차(30분 녹음)를 만들지 않는다.

## 7. 이미 폐기된 길 — prompt-biasing

**학습 없는 값싼 개인화는 실측에서 역효과였다.** whisper `initial_prompt`에 화자의
전사를 넣는 방식은 적응 시간을 늘릴수록 CER이 나빠졌고, 한 화자는 1분 적응에서
프롬프트를 되뇌며 폭발했다. 수치는 [`scripts/asr_eval/README.md`](../../scripts/asr_eval/README.md)
"개인화 커브 실측" 절.

**결론: 진짜 음향 파인튜닝 말고는 길이 없다.** 개인화를 싸게 하려는 시도는 이미
한 번 했고 실패로 고정됐다.

## 8. 조각의 수명 — 버전 관리와 폐기는 같은 장치다

버전 관리·배포 주기(무엇을 올릴 것인가)와 폐기 시점(무엇을 내릴 것인가)을 따로
풀려고 하면 둘 다 어렵다. 하나의 장치로 합쳐진다.

### 결정 7 — 환자별 holdout 승격 게이트

```
새 조각 학습 → 그 환자의 최근 holdout에서 3자 비교
   공통 모델  vs  현재 조각  vs  새 조각
     → 이긴 것만 서빙에 올린다. 공통 모델이 이기면 조각을 버린다.
```

이 하나로 세 가지가 동시에 풀린다.

| 문제 | 이 게이트가 하는 일 |
|---|---|
| "환자 A의 모델이 이상해졌다" | 애초에 올라가지 않는다(사전 방어). 사후 감지는 별도 |
| 회복해서 조각이 낡음 | 발화가 정상에 가까워지면 공통 모델이 이겨 **자동 폐기**된다 |
| 롤백 | 이전 조각이 항상 후보로 남아 있다 |

부속 규칙 둘.

- **갱신은 시간이 아니라 데이터량 기준.** "새 적격 발화 N개 누적 시 재학습". 안 쓰는
  환자는 재학습도 돌지 않는다
- **학습 윈도우는 최근 것만.** 오래된 발화는 학습에서 빼되 **보관은 유지**한다 —
  회복 추세의 근거 데이터다

> ⚠️ **가장 아픈 운영 비용은 따로 있다.** 공통 모델을 바꾸면 **모든 조각이 무효**가
> 된다. LoRA는 특정 베이스 가중치에 붙는 델타라 베이스가 바뀌면 전원 재학습이다.
> 3층을 켜는 순간부터 공통 모델 갱신은 무거운 결정이 되므로, 갱신 주기를 낮게
> (분기 1회 수준) 유지할 각오가 필요하다.

### 결정 8 — 삭제 요구는 조각 재학습까지 포함한다

화자별 분리 저장 덕에 원본 발화는 조각만 지우면 되지만, **개인화 조각에는 그 발화가
이미 가중치로 녹아 있다.** 삭제 요구 = 원본 삭제 + 해당 환자 조각 폐기 + 재학습.
조각이 작아 비용은 크지 않지만, 정책으로 명시하지 않으면 나중에 놓친다.

## 9. 착수 전 갖춰야 할 것

1. **2층 안정화** — 608 파인튜닝이 채택 가능한 공통 모델을 낼 것
2. **음향 채점기** — 개인화와 무관한 고정 잣대(결정 6). **3층보다 먼저** 온다
3. **개인화 평가 프로토콜** — 화자별 홀드아웃. 2층에서 겪은 실수(dev 없이 test로
   체크포인트 선택)를 3층에서 반복하지 않는다. 화자당 데이터가 적어 이 함정에
   빠지기 더 쉽다. 결정 7의 승격 게이트가 이것 위에 선다
4. **자유 발화 평가셋** — 지금은 대화 모드 성능을 **측정조차 못 한다**(10절)
5. **콜드 스타트 정책** — 신규 환자는 개인화 데이터가 없다. 공통 모델로 시작해
   일정량이 모이면 전환하는 흐름(등록 장벽을 만들지 않는다)

## 10. 미해결

### 대화 모드는 라벨이 없다 — 학습보다 **측정**이 먼저다

개인화 이득이 가장 큰 곳인데 학습 데이터를 만들 수 없다. 세 갈래가 있고 순서가 정해졌다.

| | 내용 | 판단 |
|---|---|---|
| A | 연습·검사에서 배운 조각을 대화에 전이 | **1순위.** 화자의 음향 특성은 과제와 무관해 상당 부분 전이된다. 낭독→자유발화 갭은 남지만 공짜다 |
| B | 대화 중 확인 발화("○○라고 하셨나요?")로 라벨 수집 | 대화 흐름을 끊는다. 효과를 모르는 채 넣기엔 비용이 크다 |
| C | 자유 발화 **평가셋** 확보 | 학습이 아니라 측정 문제 — **이게 먼저다** |

**C가 선행이다.** 현재 문장 CER은 대본 낭독 대리치라 자유 발화에서 얼마나 나쁜지
모른다. 측정이 없으면 A가 전이됐는지, B가 값어치를 했는지 판단할 수단이 없다.
([STT 자유 인식 부채](../history/20260702_STT_tech_debt.md)와 같은 뿌리)

### 보호자 확인 화면을 만들 것인가

방식은 정해졌다(결정 3 — 1탭 판정). 남은 것은 **보호자에게 새 할 일을 만들 것인가**라는
제품 가치관 판단이다. 데이터 측면에선 명확한 이득이고, "알림 없이 보호자가 원할 때만
들어가는 관찰 화면"이면 회고 아크와 톤이 맞는다. 결정은 개인화 착수 시점으로 미룬다.
