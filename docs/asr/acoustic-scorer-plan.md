# 음향 채점기 개발 계획 — 개인화보다 먼저 오는 것

- **작성**: 2026-08-21
- **상태**: 계획. 0단계(실측)부터 착수 가능
- **왜 지금**: [개인화 설계](personalization-design.md) 결정 6이 이것을 **3층보다 먼저**로
  못 박았다. 고정 잣대를 자체 확보하기 전에는 개인화를 서빙에 올리지 않는다
- **성격**: 결정 기록. 수치는 [파인튜닝 대장](608-finetune-log.md)에 적는다

## 1. 출발점 — 채점기는 이미 있다

빈칸이 "엔진"이라고 생각하면 계획이 어긋난다. 음향 채점 경로는 **이미 물려 있고
운영 중**이다.

| 조각 | 위치 | 상태 |
|---|---|---|
| 엔진 추상 인터페이스 | `ai-service/interfaces/pronunciation_assessor.py` | 있음 — 엔진 교체를 이미 상정 |
| Azure 발음평가 구현 | `ai-service/infra/azure_pronunciation.py` | 있음 |
| 엔드포인트 | `ai-service/routers/pronunciation.py` → `POST /pronunciation` | 있음 |
| 백엔드 프록시 | `backend/src/ai-proxy/ai-proxy.controller.ts` | 있음 |
| 프론트 채점 정책 | `.../quiz/domain/pronunciationScore.ts` `evaluateFromAzure` | 있음 |
| 문자열 폴백 | 같은 파일 `evaluateSpeech` ← `speechScore.ts` | 있음 |
| 호출 지점 | `.../quiz/application/useMixedQuizSession.ts` (3곳) | 있음 |

즉 **음향 점수가 1순위, 문자열 근접도가 폴백**인 2단 구조가 이미 돌고 있다.

그래서 이 계획의 주제는 엔진을 만드는 것이 아니라 **① 지금 것이 우리 대상에서
실제로 작동하는지 재고 ② 오염 경로를 닫고 ③ Azure 의존에서 벗어나는 것**이다.

## 2. 실제로 비어 있는 것 넷

### (1) 검증이 없다 — 가장 큰 구멍

Azure Pronunciation Assessment는 **외국어 학습자(L2)용**으로 설계됐다. "원어민
발음에서 얼마나 벗어났는가"를 재는 도구다. 우리 사용자는 **구음장애·실어증 노인**이고,
정의상 그 잣대에서 크게 벗어나 있다.

여기서 나올 수 있는 실패는 조용하다. 점수가 전원 0~20점에 몰리면(**바닥 효과**)
채점기는 여전히 숫자를 내지만 두 가지가 동시에 죽는다.

- 환자에게 보이는 유일한 피드백인 5단계 등급이 **전부 `retry`**가 된다.
  이 앱의 설계 원칙("비처벌·성공 경험") 자체와 충돌한다
- 보호자용 진전 추적이 무의미해진다. 좋아져도 바닥에서 안 움직인다

**한 번도 안 재봤다.** `ai-service/tests/test_azure_pronunciation.py`는 전부 speechsdk
mock이라 파싱·파일정리만 검증한다. 실제 Azure가 한국어 구음장애 발화에 무엇을
돌려주는지는 이 저장소 어디에도 기록이 없다. 재는 데 필요한 건 다 있다.

**코드를 읽다 나온 구체적 실패 경로 둘** — 실측 전에도 확인되는 사실이다.

**NoMatch는 부분 점수가 아니라 전 점수 0이다.** `azure_pronunciation.py`의 NoMatch
분기가 accuracy·fluency·completeness를 모두 `0.0`으로 돌려주고, 프론트는 그것을
`retry` 등급으로 매핑한다. 중증 발화에서 NoMatch가 잦으면 환자는 "다시 한 번
해볼까요?"만 반복해서 받는다. **그래서 0단계는 점수 분포뿐 아니라 NoMatch 발생률을
따로 세야 한다.**

**completeness가 인식 기반이라 문장 점수에 전사 의존이 남아 있다.** `enable_miscue=True`는
빠뜨림/덧붙임을 *인식된 단어와 참조의 대조*로 판정한다. 즉 completeness는 "무엇을
말했다고 인식했는가"에 의존하는데, 우리 대상은 바로 그 인식이 무너지는 집단이라
제대로 말해도 거짓 `Omission`이 날 수 있다. 그리고 문장 종합점수가 이렇다:

```ts
// pronunciationScore.ts — azureComposite
return Math.round(azure.accuracyScore * 0.6 + azure.completenessScore * 0.4);
```

**문장 점수의 40%가 인식 기반**이라는 뜻이다. 결정 6이 채점 경로에서 몰아내려던
전사 의존이 Azure 내부에 남아 있었다. 단어 모드는 `accuracyScore`만 쓰므로 무관하다.

### (2) 폴백이 잣대를 바꾼다

Azure 실패 시 `evaluateSpeech`(문자열 편집거리)로 폴백한다. 이건 **다른 것을 재는
다른 자**다. 같은 환자의 같은 과제 점수가 그날 네트워크 상태에 따라 달라진다면
회차 간 비교가 성립하지 않는다.

개인화(3층)를 켜면 이게 오염 경로가 된다 — 개인화 전사가 폴백 채점에 들어가면
"쓸수록 점수가 오른다"가 실력 향상과 구분되지 않는다(결정 1·6). **지금도 문제이고,
개인화 이후엔 치명적이다.**

### (3) Azure 종속이 영구화된다

결정 6이 명시한 대가다. 문항당 API 호출이고, 오디오가 외부로 나가며,
[3단 비용계층](608-finetune-log.md) 설계의 전제와 맞물린다.

### (4) 다국어 부채

발음 채점기는 언어별 음소 체계에 묶인다. 영어·스페인어 확장 시 언어별 플러그인으로
재구현이 필요하다 — 인터페이스가 이미 `lang`을 받는 건 그 대비다.

## 3. 채점기가 만족해야 할 것

무엇을 만들든 이 넷으로 판정한다. 순서가 곧 중요도다.

| # | 요구 | 왜 |
|---|---|---|
| 1 | **판별력** | 목표를 말한 발화와 다른 것을 말한 발화를 가른다. 못 가르면 채점이 아니다 |
| 2 | **해상도** | 점수가 한쪽 끝에 뭉치지 않는다. 뭉치면 진전이 안 보인다 |
| 3 | **재현성** | 같은 오디오를 두 번 재면 같은 점수 |
| 4 | **개인화 불변성** | 환자별 조각과 독립. **동결된 공통 모델**로만 돈다 |

4번이 이 문서의 존재 이유다. 1~3만 보면 "Azure 잘 쓰면 되지"로 끝난다.

## 4. 0단계 — 실측 (지금 착수 가능, 새 데이터 불필요)

이 프로젝트의 규율은 **고치기 전에 실측**이다([등급 부채 문서](../history/20260816_speech_grade_threshold_debt.md)가
그 규율로 스스로의 오진을 잡았다). 여기도 같게 간다.

### 쓸 자산과 그 한계

| | |
|---|---|
| 평가 오디오 | 608 test 417세그 (단어 146 · 문장 271 · 화자 10) — 참조 텍스트 있음 |
| **없는 것 1** | **건강 대조군.** 608 전 1632건이 장애 발화다(실측 확인) |
| **없는 것 2** | **중증도 라벨.** `disease_type`·`category`뿐이라 "점수가 중증도를 따라가는가"는 못 잰다 |
| **없는 것 3** | 자발 발화. 전 건이 `Read aloud scripts` |

대조군은 **직접 녹음해 만든다.** test 문항을 비장애인 1~2명이 읽으면 된다(30~40분,
비용 0). 이게 점수 분포의 상단 기준선을 준다. 없으면 "60점이 낮은 건가"를 말할 수 없다.

### 네 가지 측정

**A. 분포 — 바닥 효과가 있는가**
`accuracy_score` 히스토그램을 단어/문장으로 나눠 본다. 5등급 매핑 후 등급 분포도
같이 본다. 대조군 녹음과 겹쳐 그린다.
**`NoMatch` 비율을 따로 센다**(전 점수 0으로 들어가 분포를 왜곡한다).
`accuracy`와 `completeness`도 **분리해서** 본다 — 뒤엣것은 인식 기반이라 성격이 다르다.

**B. 참조 대조 — 채점기가 오디오를 실제로 보는가** ← 핵심
같은 오디오를 두 번 채점한다: **정답 참조**로 한 번, **음절 수를 맞춘 무작위 오답
참조**로 한 번. 제대로 된 채점기라면 앞이 뚜렷하게 높아야 한다.

라벨 없이 타당도를 재는 유일한 방법이고, 가장 나쁜 실패 방식을 직접 겨눈다 —
채점기가 오디오를 거의 안 보고 참조 텍스트 길이에 따라 그럴듯한 숫자를 뱉는 경우.

**C. 두 잣대의 일치도 — 폴백이 얼마나 다른 자인가**
같은 발화에 대한 Azure 점수와 `app_scorer.py` 오류율의 순위상관(Spearman).
낮으면 폴백이 발생할 때마다 환자 점수가 튄다는 뜻이다.

**D. 비용·지연** — `stt` 모드는 실측됐다(2026-08-22): 417건 4분 11초, 약 $0.34.
문항당 0.6초 · $0.0008이다. `pa` 모드는 아직이다.
417건 실호출로 문항당 지연과 단가를 잰다. 검사 1회 문항 수 × 환자 수로 환산한다.

### 판정 규칙 — 결과를 보기 전에 못 박는다

결과를 본 뒤 기준을 정하면 유리한 쪽으로 해석하게 된다. 8차·9차에서 쓴 규율과 같다.

| 측정 | 통과 | 실패 시 할 일 |
|---|---|---|
| A 분포 | `retry` 등급 비율 ≤ 40% **그리고** 대조군과 환자군 중앙값이 겹치지 않음 | 임계값 재조정(작음) → 안 되면 자체 채점기를 앞당긴다 |
| A' NoMatch | 발생률 ≤ 10% | 0점 대신 **채점 불가**로 보낸다(1단계와 합류) |

> **A′ 실측 완료 (2026-08-22): `pa` 모드 0.2% — 통과.** 트리거는 발동하지
> 않는다. `stt` 모드로 먼저 잰 5.5%(단어 11.6%)는 앱이 쓰지 않는 모드였다.
> 참조 텍스트를 함께 주면 Azure가 거의 포기하지 않는다. 상세: 아래 4-2절.

| B 대조 | 정답참조 − 오답참조 평균차 ≥ 20점, 분리 AUC ≥ 0.80 | **Azure를 채점 경로에서 내린다.** 이건 재조정으로 못 고친다 |
| C 일치 | Spearman ≥ 0.6 | 1단계(폴백 차단)를 최우선으로 올린다 |
| D 비용 | 3단 비용계층 예산 안 | 캐싱·문항 선별로 호출 수를 줄인다 |

## 4-2. 0단계 결과 (2026-08-22)

측정: `scripts/asr_eval/azure_eval.py --mode pa`, 608 test 417세그, ko-KR.
정답 참조 1회 + 음절 수를 맞춘 오답 참조 1회 = 834호출, 약 $0.68, 각 6분.

### 판정 요약

| 측정 | 기준 | 결과 | 판정 |
|---|---|---|---|
| A 분포 | retry ≤ 40% **그리고** 대조군과 중앙값 분리 | retry 단어 4.8% · 문장 8.9% / **대조군 없음** | **절반만** |
| A′ NoMatch | ≤ 10% | **0.2%** | **통과** |
| **B 대조** | 평균차 ≥ 20점, AUC ≥ 0.80 | **+59.5점, AUC 0.960** | **통과** |
| C 일치 | Spearman ≥ 0.6 | **−0.376** | **실패** |
| D 비용 | 3단 비용계층 예산 안 | 문항당 0.92초 · $0.0008 | 통과 |

### B — 통과, 그것도 압도적으로

가장 나쁜 실패 방식(채점기가 오디오를 안 보고 참조 텍스트로 숫자를 지어냄)을
직접 겨눈 측정이고, 여기서 막혔다면 Azure를 채점 경로에서 내려야 했다.

| | 정답 참조 | 오답 참조 | 차이 |
|---|---|---|---|
| accuracy 평균 (n=413) | 80.6 | 21.1 | **+59.5** |
| 앱 매핑 「정답 처리」 단어 | 93.2% | 6.2% | −87.0%p |
| 앱 매핑 「정답 처리」 문장 | 83.4% | 1.1% | −82.3%p |
| 분리 AUC | | | **0.960** |

**Azure는 오디오를 듣는다.** 같은 음성에 음절 수가 같은 다른 문장을 참조로 주면
점수가 무너진다. 기준(20점, 0.80)을 세 배 가까이 넘겼다.

> **이것이 답하지 않는 질문.** B는 "오디오를 보는가"를 재지 **"중증도를 가리는가"**를
> 재지 않는다. 구음장애 발화 사이의 경중을 구분하는지는 여전히 미측정이다.
> 그건 건강 대조군과 중증도 라벨이 있어야 한다.

### C — 실패. 두 잣대는 서로 다른 자다

Azure `accuracy`와 `app_scorer` 오류율의 Spearman이 **−0.376**이다(기준 0.6).
음의 상관 방향은 맞지만 크기가 절반이다.

**뜻**: Azure가 실패해 앱이 폴백할 때, 환자가 받는 점수는 **다른 자로 잰 값**이다.
같은 발화가 경로에 따라 다른 등급을 받는다. 사전 등록한 대로 **1단계(폴백 차단)가
최우선으로 올라간다.**

### A — 절반만 쟀다

retry 비율은 기준을 넉넉히 통과한다(단어 4.8%, 문장 8.9%). 그러나 **바닥 효과가
아니라 천장 효과가 의심된다** — 구음장애 발화의 93.2%(단어)가 앱에서 「정답
처리」로 나온다. 이게 정상인지 관대한 건지는 **건강 대조군 없이는 말할 수 없다.**

오답 참조 실행이 하단 기준선은 준다(단어 정답처리 6.2%). 눈금이 위아래로 안
붙어 있다는 것은 확인됐다. 하지만 "비장애 발화는 몇 점인가"는 여전히 공백이고,
그것이 「점수가 회복을 반영하는가」의 전제다.

**남은 일: 대조군 녹음.** test 문항을 비장애인 1~2명이 읽는다. 30~40분, 비용 0.

### A′ — 정정한다

**앞서 대장 §1-2에 기록한 「단어 NoMatch 11.6% → 채점 불가 도입 발동」은
`stt` 모드 수치였다.** 앱이 실제로 쓰는 `pa` 모드에서는 **0.2%(417건 중 1건)**로,
기준을 크게 통과한다. 참조 텍스트를 함께 주면 Azure가 거의 포기하지 않는다.

사전 등록한 트리거는 **발동하지 않는다.** NoMatch를 0점으로 기록하는 것은
여전히 원리적으로 틀렸지만(0점은 "못했다"고 말하는데 실제로는 "못 쟀다"이다),
빈도가 0.2%라 우선순위는 낮다. 1단계에 남기되 최우선은 C가 가져간다.

### 새로 알게 된 것 ① — `pa` 모드는 전사를 부풀린다

같은 오디오, 같은 Azure인데 참조 텍스트를 주느냐로 전사 품질이 갈린다.

| | `stt` (참조 없음) | `pa` (참조 줌) |
|---|---|---|
| 단어 정확 일치율 | 62.3% | **94.5%** |
| 문장 CER | 0.268 | **0.117** |
| NoMatch | 5.5% | 0.2% |

**+32%p다.** Azure PA의 전사는 참조 텍스트로 강하게 제약된다. 이것이
[두 목표 문서](../learning/dysarthria-agent/02-two-goals.md)가 경고한 그
현상이다 — 채점기가 자기가 고쳐 놓고 잘했다고 하는 것.

그래서 `--mode pa`의 전사를 ASR 비교에 쓰면 안 된다. 스크립트가 모드를 나눈
이유이고, 이제 실측으로 확인됐다.

### 새로 알게 된 것 ② — `completeness` 40%는 변별에 기여하지 않는다

`pronunciationScore.ts`의 문장 종합점수는 `accuracy*0.6 + completeness*0.4`다.
같은 캐시로 세 가지를 비교했다(문장 n=271).

| 종합 방식 | 정답 참조 | 오답 참조 | 차이 | AUC |
|---|---|---|---|---|
| **accuracy 단독** | 78.1 | 23.6 | +54.5 | **0.962** |
| 앱 공식 (0.6/0.4) | 76.8 | 17.0 | +59.8 | 0.961 |
| completeness 단독 | 74.8 | 7.1 | +67.7 | 0.951 |

**accuracy만 써도 AUC가 같다(0.962 대 0.961).** completeness 40%가 사서 오는
변별력은 0인데, 그것은 miscue 기반이라 위에서 본 **부풀려진 전사에 의존한다.**
결정 6이 없애려던 그 의존이 문장 점수의 40%를 차지하고 있다.

게다가 오답 참조에서 completeness가 0인 비율이 75.3%다 — 참조가 어긋나면
그냥 0으로 붕괴한다. 이 항은 발음의 척도라기보다 **참조 일치의 척도**에 가깝다.

> **다만 이 측정이 답하지 않는 것.** completeness의 본래 목적은 「빠뜨림에
> 정직하기」다(코드 주석). 환자가 문장 일부를 생략했을 때 그걸 잡아내는지는
> B로 알 수 없다 — B는 참조를 통째로 바꾼 것이지 일부를 뺀 게 아니다.
> **비중 0.4를 없애자는 결론으로 바로 가지 말고**, 생략 시나리오를 따로
> 만들어 재라(대조군 녹음 때 문항 일부를 의도적으로 생략해 읽으면 된다).

## 4-3. 측정 B′ — 근접 단어 대조 (2026-09-26, 결과 보기 **전에** 적는다)

**B가 답하지 않은 질문.** B의 오답 참조는 **음절 수만 맞춘 무작위 단어**였다. 실어증의
실제 오류는 무작위가 아니라 **가까운 단어**다 — 소리가 비슷하거나(사탕→사자) 뜻이
비슷하다(사과→배). 이름대기에서 앱이 가려야 할 것은 바로 이것이다. B의 6.2%는 이
경우의 하한일 뿐이다.

**방법.** `scripts/asr_eval/azure_foil_eval.py`. 608 test 단어 146행에 대해
`build_target_foils.py`가 만든 foil을 참조로 준다(단어당 종류별 최대 3개).

| 종류 | 참조 | 오통과율 분모 |
|---|---|---|
| 음운 근접 | 앱 표적 단어 중 음소 유사 거리가 가장 가까운 단어 | **넣는다** |
| 의미 근접 | 앱 `WORD_CATEGORY` 같은 범주(앱 풀에 있는 28종만 가능) | **넣는다** |
| 음소 착어 | 자모 하나를 다른 조음 그룹으로 바꾼 말 | 따로 보고(구음장애 왜곡과 구분 불가) |

"A를 말한 오디오 + 참조 B"는 흉내가 아니라 **"목표 B에 환자가 A를 말함" 그 자체**다.
남는 차이는 A가 608 화자가 맞게 읽으려 한 발화라는 점뿐이다. 정답 참조 점수는 B의
캐시(`_azure_pa_cache.jsonl`)를 재사용한다. 호출 984건, 오디오 8.6분, 약 $0.14.

**앱 판정을 그대로 쓴다.** 단어는 `accuracy ≥ 60`이면 정답, 인식 텍스트가 비면 채점
불가(`evaluateFromAzure`). 채점 불가는 오통과율 분모에서 뺀다(통과도 탈락도 아니다).

**판정 규칙 — 근접(음운+의미) 오통과율.** 목표 단어 검증(대장)과 같은 띠를 쓴다.

| 근접 오통과율 | 판정 | 할 일 |
|---|---|---|
| ≤ 5% | 문제없음 | 기록만 한다 |
| 5% ~ 10% | 주의 | 비대칭 오류 정책(TODOS 2번)에서 다룬다 |
| > 10% | **결함** | 이름대기가 근접 단어 대치를 못 잡는다. 인식 텍스트 대조 같은 보강을 설계한다 |

결과는 이 절에 이어 쓴다.

### 하다가 정한 것 하나 — 보호자가 유일하게 남은 잣대다

채점 불가 문항에도 보호자 정정 버튼을 낸다. 처음엔 "판정이 없는데 무엇을
정정하나" 싶어 숨기려 했는데, 거꾸로다. 기계가 판정을 못 낸 자리에서 옆에 있는
사람은 **폴백이 아니라 유일하게 남은 잣대**다 — 직접 듣고 낸 판정이라 문자열
채점처럼 "다른 것을 재는" 문제가 없다.

정정하면 `unscored`가 떨어지고 정확도 집계에 들어간다. 점수(`score`)는 여전히
없다 — 사람은 정오답을 말했지 0~100점을 말한 게 아니다.

부수 효과: 등급 부채 문서가 다룬 **문장 모드 `great` 도달 불가** 문제는 폴백
경로에만 남게 되어 우선순위가 내려간다. 그 문서의 결론을 다시 볼 것.

## 6. 2단계 — 자체 채점기

Azure를 대체한다. 인터페이스(`IPronunciationAssessor`)가 이미 있으므로 **구현체
하나를 추가하는 일**이고 앱 코드는 안 바뀐다.

방향은 **강제 정렬 + GOP(Goodness of Pronunciation) 계열**이다. 참조 텍스트를 아는
과제이므로, 음향 모델의 프레임별 사후확률을 목표 음소열에 정렬해 "이 음소가 이만큼
그럴듯했는가"를 낸다. 전사를 거치지 않는다 — 결정 6이 요구하는 형태 그대로다.

**함정이 하나 있고, 이게 설계의 핵심이다.**

> 채점기의 기반 모델이 608로 구음장애에 능숙해질수록, 채점기는 구음장애 발화를
> **더 관대하게** 본다. 그러면 모델을 개선할 때마다 환자 점수가 오른다 — 실력
> 향상과 구분되지 않는다. 개인화에서 막으려던 확증 편향이 한 층 아래에서 재발한다.

그래서:

- 채점기의 기반 모델은 **동결하고 버전을 박는다.** 2층 모델이 좋아져도 채점기는
  자동으로 따라가지 않는다
- 채점기 갱신은 **의도적 사건**으로 다룬다 — 결정 7의 승격 게이트와 같은 성격
- 개인화 조각은 채점기에 **절대** 로드하지 않는다(요구 4)

검증은 0단계와 **같은 프로토콜**로 하고, Azure를 비교 대상으로 둔다. 잣대를 바꾸면
비교가 성립하지 않는다.

## 7. 3단계 — 점수의 버전 관리

점수는 채점기 버전에 묶인다. 이걸 명시하지 않으면 진전 그래프가 조용히 거짓말한다.

- 저장되는 점수에 **채점기 버전을 함께 기록**한다
- 진전 추적·회차 비교는 **같은 버전 안에서만**
- 버전을 올릴 때는 보관된 오디오를 재채점하거나, 전환 시점을 그래프에 표시한다
