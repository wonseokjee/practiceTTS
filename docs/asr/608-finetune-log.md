## 읽는 법 — CER을 가로로 비교하지 말 것

**같은 실행의 "전 → 후"만 유효한 비교다.** test set이 배치마다 다르기 때문이다.

- 2차 test는 단어 세그먼트(앱 최약점)를 포함해 1차보다 **어렵다**. 그래서 후처리
  CER 0.656이 1차의 0.424보다 나쁘게 보이지만, 두 수치는 서로 다른 시험지 점수다.
- 3차부터 화자 split을 파일에 봉인(`speaker_split.json`)했다. 그 이전 배치와는
  test 화자 구성 자체가 다르다.
- 4차부터는 봉인된 split을 이어 쓰므로 **3차와 4차는 비교 가능**하다(test 화자 동일).

판정 기준은 "후 < 전"이면 파인튜닝이 먹혔다는 것뿐이다.

## 1. 학습 실행 기록

| 회차 | 학습 규모 | test set | CER 전 → 후 | 개선 | 비고 |
|---|---|---|---|---|---|
| 스모크 | 40분·178세그 | 소량 | — (train loss 0.003) | 이득 0 | 과적합(암기). 노트북 동작 검증용 |
| 1차 | 372세그·화자~20 | 35세그·화자3 | **0.816 → 0.424** | −47% | 첫 유효 학습 |
| 2차 | 751세그·화자21 | 94세그·화자5 | **0.816 → 0.656** | −20% | test에 단어 세그 포함 → 더 어려운 시험지 |
| 3차 | 1994세그·화자45 (train 1302) | 302세그·화자9 | **0.551 → 0.383** | −30% | loss 7.148→0.637, 4 epoch·15:44. split 봉인 첫 배치 |
| 4차 | 2347세그·화자50 (train 1543) | 325세그·화자10 | **0.519 → 0.376** | −28% | loss 6.948→0.590, 4 epoch·18:12. **1에폭에 이미 0.344, 이후 헛돎** |

### 4차 에폭별 (첫 포화 신호)

| epoch | train loss | val loss | CER |
|---|---|---|---|
| baseline | — | 6.948 | 0.5192 |
| 1 | 0.993 | 0.791 | **0.3441** |
| 2 | 0.588 | 0.636 | 0.3469 |
| 3 | 0.268 | 0.599 | **0.3438** ← 최저 |
| 4 | 0.449 | 0.590 | 0.3759 ← 채택된 값(최종 에폭) |

두 가지가 동시에 보인다.

**1) 에폭이 낭비되고 있다.** CER은 1에폭에서 사실상 끝났다(0.344). 2~4에폭은
0.344~0.347에서 맴돌다 4에폭에 0.376으로 **나빠졌다**. val loss는 계속 내려가는데
(0.791→0.590) CER은 안 내려간다 — loss와 지표가 갈라지는 전형적인 구간이다.
train loss 0.268 vs val 0.599(3에폭)은 과적합이 시작됐다는 뜻이다.

**2) 최고 체크포인트를 버리고 있었다.** 노트북이 `save_strategy="no"`라 **마지막
에폭 가중치**를 쓴다. 그래서 0.3438을 얻고도 0.3759를 기록했다. 공짜로 잃던
−8% 상대 개선이다. → 수정함(아래 5절).

> **3차와 비교 가능한가**: 부분적으로만. 봉인 split 덕에 test 화자 9명은 그대로지만
> 신규 화자 1명이 test에 추가돼 302→325세그로 늘었다. baseline CER이 0.551→0.519로
> 달라진 게 그 증거다. 시험지가 **거의** 같지 완전히 같지는 않다.

**해석**: 751 → 1994세그(2.6배)에서는 개선폭 −30%로 포화 신호가 없었다. 그런데
1994 → 2347세그(+18%)인 4차에서 개선폭이 −28%로 **늘지 않았다.** 첫 정체 신호다.

다만 단정하기엔 이르다. 4차에 더한 데이터는 대부분 서술문이고 test도 서술문
100%다. 즉 **"이미 잘하는 종류를 더 넣었더니 안 늘었다"**는 해석이 가장 자연스럽고,
이건 데이터 양의 포화가 아니라 **종류의 포화**일 수 있다. 5차(단어 전량)가 이
해석을 검증한다 — 단어 데이터로 단어 CER이 내려가면 양이 아니라 종류가 문제였던
것이고, 그래도 안 내려가면 진짜 포화이거나 whisper-small의 한계다.

## 3. 지금 막힌 지점 — 단어 CER을 측정할 수 없다

자체 ASR을 하는 **1순위 이유가 단어 수준 구음장애**다(608 실측: 단어나열 CER 0.70
vs 서술문 0.125 — 앱 과제가 최악 조건). 그런데:

- 1~3차 1994세그는 `task_type` 필드가 없어 재패키징 시 전부 `narrative`로 채워진다.
  **사후 재분류는 불가능하다** — 세그먼트 하나엔 문장부호가 1~2개뿐이라 전부
  wordlist로 오분류된다(실측 확인). 판정은 정렬 시점에 파일 단위로 박아야 한다.
- 4차에서 얻은 wordlist는 47세그뿐이고, 화자 단위 split 결과 **전부 train 쪽에
  몰려 test 단어 세그가 0개**다. 즉 4차 학습으로는 문장 CER만 나온다.

→ 5차를 wordlist 전량으로 잡은 이유다.

```
TS01.zip (원본 425 wav)
  → select_608_batch2.py --task-type wordlist   (완료분 제외 + 화자 다양성 + wav 추출)

  → prepare_colab_trainset.py --split-file ...  (배치 병합 + 화자 분리 + zip)
  → Colab (finetune_whisper_608_colab.ipynb, T4)
```

### 밟았던 함정

- **최고 체크포인트를 버리지 말 것.** 노트북이 `save_strategy="no"`라 마지막 에폭
  가중치를 그대로 썼다. 4차에서 3에폭 CER 0.3438을 얻고도 4에폭 0.3759를 기록한
  이유다. `load_best_model_at_end=True` + `metric_for_best_model="cer"` +
  `greater_is_better=False`로 수정했다. **loss 기준으로는 못 고른다** — 4차에서
  val loss는 끝까지 내려갔는데 CER은 그렇지 않았다(지표 갈라짐).

- **`--split-file`을 반드시 명시할 것.** 기본값은 `--seg-root`의 상위 폴더인데,
  병합 매니페스트를 쓰면 seg-root가 `608-audio-work`가 되어 봉인 파일을 그 상위
  (`Downloads/`)에서 찾는다. 결과적으로 화자를 새로 셔플해 **3차 train 화자가 4차
  test로 넘어간다**(누출 + 비교 불가). 정상 동작 시 로그에 `기존 45명 유지 +
  신규 5명 배정`이 찍힌다.
- **`_done_exclude.jsonl`을 배치마다 갱신할 것.** 안 하면 다음 선정이 이미 정렬한
  파일을 다시 뽑는다. `_segs_big*/segments.jsonl`의 `parent_file_id` 합집합으로 만든다.
- **원시 폴더 `_segs_big*`는 삭제 금지** — 재패키징에 필요하다.
- **정렬 중 컴퓨터 절전을 끌 것.** 2차가 9시간 걸린 원인은 처리 속도가 아니라
  절전이었다(13파일 2시간 처리 후 14번째에서 6시간 43분 무출력). 재개는
  `_attempted.txt`로 가능하니 같은 명령을 재실행하면 된다.
