# STT(음성 인식) 기술 부채

- **작성일**: 2026-07-02
- **주제**: 노인·구음장애·뇌출혈(실어증/마비말장애) 환자 대상 음성 인식
- **상태**: 미착수 (향후 과제)

## 배경

현재 STT는 브라우저 **Web Speech API**(`frontend/src/memory-link/patient/infrastructure/SttService.ts`, `ko-KR`, `confidence < 0.6`이면 재시도 유도)를 사용한다. 이 방식은 정상 성인 발화로 학습된 모델이라, 대상 환자군(노인·구음장애·마비말장애)의 **병리 발화를 거의 인식하지 못하며**, confidence 게이트가 병리 발화를 전부 걸러내 "다시 말씀해주세요"만 반복시켜 환자에게 최악의 좌절 경험을 준다.

핵심 레버리지는 **"자유 받아쓰기"가 아니라 "목표 근접도 채점"으로 문제를 바꾸는 것**이다. 퀴즈·훈련은 정답(`targetWord`, 퀴즈 정답)을 미리 알기 때문에, 후보 중 근접도를 판단하면 자유 인식보다 훨씬 정확하다. 이미 `speechScore.ts`·`nameMatch.ts`에 발음 유사도 채점 로직이 있다.

이 문서는 **위 제약 채점으로 해결되지 않는 두 부채**를 기록한다.

---

## 부채 1 — 대화 모드 자유 인식

**문제**: 대화 모드(기억 훈련, `TrainingScreen`)는 자유 회상 대화라 **정답이 없다**. 제약 채점(목표 근접도)을 쓸 수 없고, 결국 **자유 음성 인식**이 필요하다. 그런데 병리 발화의 자유 인식은 난이도가 가장 높다.

**방향**:
- 파인튜닝된 서버 STT: Whisper large-v3 파인튜닝 또는 Azure Custom Speech (AI-Hub 노인/구음장애 데이터 활용)
- 자유 디코딩 + "관대한 처리·격려" 설계(부분 인식이라도 대화가 이어지게)
- 프론트: `MediaRecorder`로 녹음 → `ai-service`로 전송(Web Speech는 오프라인 폴백으로 유지 가능)

**우선순위**: 정답을 아는 과제(퀴즈·목표단어)의 제약 채점을 먼저 정비(채점 강화 → `ai-service` `/stt` 라우터 + Azure phrase hint)하고, **대화 모드 자유 인식은 그 이후**.

---

## 부채 2 — 다국어(영어·스페인어) 발음 채점기

**배경**: GlobalExpansion(다국어 확장, `docs/history/20260629_GlobalExpansion_plan.md`) 관련.

**엔진**은 영어·스페인어까지 그대로 커버된다:

| 엔진 | 영어 | 스페인어 | 판정 |
|---|---|---|---|
| Whisper (large-v3) | 최상 | 우수 | ✅ 다국어 최적 |
| Azure Speech | 최상 | 우수 | ✅ Custom Speech 언어별 지원 |
| CLOVA | 약함 | 미지원 | ❌ 한국어 전용 → 글로벌 제외 |

**문제**: 엔진(언어 코드만 교체)이나 phrase hint는 언어 무관하게 동작하지만, **발음·음소 유사도 채점기는 언어별로 새로 구현해야 한다**. 현재 `speechScore`/`nameMatch`는 **한글 자모 분해** 기반이라 영어·스페인어에 재사용 불가.

**방향** — 엔진은 공유, 채점기는 언어별 플러그인:
```
/stt (audio, lang, 목표후보)
  → Whisper/Azure (lang 지정)
  → scorer[lang]   ← ko: 자모 / en: CMU phoneme / es: 철자기반
```
- 영어: CMU 발음사전 기반 phoneme 유사도. 병리 발화 대응 자원(UASpeech·TORGO·Speech Accessibility Project 등)이 오히려 한국어보다 풍부.
- 스페인어: 철자-발음이 규칙적이라 채점이 상대적으로 쉬움.

---

## 엔진 선택 및 이전 전략 (GPU 관점)

**현재 GPU 미보유 → Azure(클라우드)로 시작한다.** "Whisper = 반드시 자체 GPU"가 아니라, **자체 호스팅 Whisper**만 GPU가 필요하다는 점에 유의.

| 방식 | GPU | 특징 | 판정 |
|---|---|---|---|
| Azure Speech | 불필요 | TTS 통합, phrase hint, Custom Speech 도메인 적응 | ✅ 지금 최선 |
| OpenAI Whisper API | 불필요 | OpenAI 호스팅. 커스터마이즈·phrase hint·스트리밍 약함 | △ 간편하나 제약 |
| 관리형 Whisper (Groq·Replicate 등) | 남의 GPU | 자체 GPU 불필요 | △ 비용·의존 |
| Whisper 자체호스팅 (CPU) | 없음 | large는 너무 느림 → 병리 발화 부적합 | ❌ 비추 |

**Whisper 자체호스팅 이전 조건 (필수 아님)**: GPU 확보 **AND** 다음 중 하나가 강해질 때 —
- 병리 발화 **파인튜닝** 통제력이 절실 (Azure Custom Speech보다 자유로움)
- 의료 음성 **온프레미스/프라이버시** 요구 (클라우드 전송 금지 규정 등) ← 결정적 요인
- **비용**: 사용량이 커져 건당 과금보다 자체 GPU가 저렴
- **오프라인** 동작 필요

반대로 이 필요가 약하면 Azure Custom Speech로도 도메인 적응이 되므로 **계속 Azure로 충분**하다. "GPU 생겼으니 무조건 Whisper"는 아니다.

**핵심 설계 원칙 — 엔진 어댑터로 교체 가능하게**: `/stt` 라우터에 엔진 어댑터 계층을 두어 엔진을 감춘다. 그러면 Azure로 시작해도 나중에 Whisper 이전이 어댑터 구현 교체로 끝나며, 호출부·채점기는 그대로 재사용된다. (프론트는 이미 `ISttService` 인터페이스 존재)

```
프론트 → /stt(audio, lang, 후보) → [엔진 어댑터: Azure | Whisper] → scorer[lang]
                                    ↑ 여기만 바꾸면 이전 완료
```

## 공통 원칙

- **완벽한 병리 발화 전사는 불가능**하다. "관대한 채점 + 격려" 설계(근접하면 성공, 실패해도 부드러운 재시도)가 기술만큼 중요하다.
- 평가 지표는 WER(단어오류율)이 아니라 **과제 성공률·목표 근접도·재시도 횟수·좌절 이벤트**.
- 음성 데이터의 **프라이버시·동의** 처리 필수. 보호자가 정답을 확인해주는 순간을 라벨링 데이터로 축적하면 지속 개선 루프가 된다.

## 로드맵 (권장 순서)

1. **단기**: 기존 음소 채점(`speechScore`/`nameMatch`)을 병리 발화에 관대하게 강화 + confidence 게이트 완화
2. **중기**: `ai-service`에 `/stt` 라우터 추가, Azure(또는 Whisper) 서버 STT 전환 + 목표단어 phrase hint
3. **부채 1**: 대화 모드 자유 인식(파인튜닝 서버 STT)
4. **부채 2**: 다국어 확장 시 언어별 채점기 플러그인(en/es)
