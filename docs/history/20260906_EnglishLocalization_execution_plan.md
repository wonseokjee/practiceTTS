## 0. 왜 다시 쓰는가

전략 문서(2026-06-29)의 **결정은 그대로 유효하다** — 미국 1차, `en-US` 단일 시작,
웰니스 포지셔닝으로 FDA 트랙 회피. 여기서 다시 다투지 않는다.

다시 쓰는 이유는 **그 문서의 Phase 0 추정이 지금 코드와 맞지 않아서**다.
2026-06-29 이후 들어온 것들:

- QAB 8개 하위검사 체계(`loc`/`word`/`sentence`/`naming`/`repeat`/`reading`/`spell`/`ddk`)
- 음향 발음 채점기(Azure accuracy 단일 자) + 문자열 폴백 **금지** 결정
- 글자조합(`spell`) 검사 — 한글 음절 타일 과제
- 세션 내 적응 레벨(문항 단위) + 음절 기반 난이도 밴드
- 단서 위계(`cue_level`) — 음소 단서가 자모 이름("첫소리는 시옷이에요")

전략 문서는 i18n을 "문자열 추출 + 프롬프트 번역"으로 봤다. **지금은 그게 작업의
절반도 안 된다.** 나머지 절반은 한국어 음운론에 묶인 채점·난이도 로직과,
언어가 아니라 **지역**에 묶인 것들(시간·인증·이름)이다.

## 1. 판정 원칙 — 세 갈래로만 나눈다

| 갈래 | 뜻 | 비용 |
|---|---|---|
| **옮김** | 값만 갈면 된다(문자열·음성 코드·slug) | 낮음, 기계적 |
| **재구현** | 같은 개념이 영어에도 있으나 구현이 못 넘어간다 | 중간, 설계 있음 |
| **재설계** | 개념 자체가 영어에 없다 | 높음, 결정 필요 |

**"재설계"를 "재구현"으로 착각하면 계획이 무너진다.** 이 문서에서 재설계는 둘뿐이다
(글자조합, 문장이해 통사구조). 나머지는 전부 옮김이거나 재구현이다.

**그리고 i18n은 언어만이 아니다.** §3의 0-5·0-6과 §7이 다루는 것들(주 시작 요일,
타임존, 이름 치환, 소셜 로그인)은 번역과 무관하지만 미국 사용자 한 명에게
곧바로 틀린 값을 보여준다. 이쪽이 문자열보다 조용히 깨진다.

## 3. Phase 0 — 되돌리기 비싼 것 (사용자 0명일 때만 싸다)

**착수 조건 없음. 지금 해도 된다.** 영어판을 실제로 만들지 않기로 해도 손해가 없다.

> **범위 정정(2026-09-12, §14 D2-A)**: 위 문장은 **데이터 형태**(0-1 컬럼)·0-5·0-5b·0-6에만 해당한다. 0-2·0-3·0-4·0-5c·0-5d(언어 배관)는 코드 기본값이라 나중에 해도 비용이 같고 한국판 이득이 없어 **영어판 게이트 뒤**로 옮겼다. 이후 0-2·0-3은 이미 PR(#162·#164)로 구현·테스트돼 있어 **머지 후보**로 돌렸다(§15).

### 0-1. 로케일 컬럼 — **환자와 보호자를 나눠서** (커밋 1개)

> **결정(2026-09-06)**: 로케일을 하나가 아니라 **둘**로 저장한다 —
> `patient_locale` / `caregiver_locale`.

- 파일: `backend/src/quiz/entities/qab-result.entity.ts` + ~~프로필 엔티티~~ **`backend/src/auth/entities/user.entity.ts`** + 새 마이그레이션
- **정정(2026-09-12, §13 OV-6)**: 프로필 행은 보호자가 프로필을 처음 저장할 때 lazy 생성된다(`profile.service.ts:103-114`) — 저장 안 한 환자는 값이 없다. 항상 존재하는 **`users` 행**에 둔다: 환자 행 `patient_locale`·`timezone`·`week_start`, 보호자 행 `caregiver_locale`, 전부 NOT NULL 기본값. `qab_results.answered_at`도 이 마이그레이션에(§13 OV-5)
- `varchar(8)`, 기본 `'ko-KR'`, NOT NULL
- **`qab_results`에는 `locale` 하나만 쓴다** — 문항을 푼 것은 환자이므로
  `patient_locale`의 세션 고정값(§7-7의 결정 B)을 적는다. 보호자 로케일은
  결과 행에 뜻이 없다
- **타임존과 주 시작 요일도 같이 얼린다**(2026-09-06, 외부 의견 수용).
  집계할 때마다 프로필의 *현재* TZ로 계산하면, 보호자가 TZ를 한 번 고치는 순간
  **지난달 리포트 숫자가 소급으로 바뀐다.** 여행·기기 오설정·VPN으로 **한국
  사용자에게도** 생길 수 있어 §9의 "한국어판 동작 변경 금지"와 충돌한다.
  로케일을 얼리기로 해놓고 같은 성질의 값을 안 얼리는 건 비일관이다
- **이유**: 이 테이블은 언어 개념이 전혀 없다. 영어 사용자가 한 명 들어오는 순간
  두 언어의 정답률·레벨이 같은 축으로 집계된다. `manifest_version`(M23)을 넣은 것과
  **정확히 같은 이유**다 — 경계를 나중에 되짚을 방법이 없어진다.
- 소급 채우기는 자명하다(기존 행은 전부 한국어). 나중에 하면 자명하지 않아진다.
- **0-5의 타임존·주 시작 요일과 한 마이그레이션에 묶는다.**

#### 왜 지금 나누는가

미국은 다국어 가정이 정상이다. **1.5세대 한인 보호자(영어)와 이민 1세대
부모(한국어)는 이 앱의 가장 개연성 높은 초기 영어권 사용자다.** 로케일이 하나면
둘 중 하나는 반드시 자기가 못 읽는 화면을 받는다 — 환자 화면을 한국어로 맞추면
보호자의 주간 리포트도 한국어로 뜬다.

나중에 쪼개면 **이미 쌓인 행의 뜻을 바꿔야 한다.** 이 문서가 경계하는
"되돌리기 비싼 것"의 정의 그대로다. 마이그레이션을 아직 안 썼으므로 지금이 가장 싸다.

#### 어느 기능이 어느 쪽을 따르는가

답이 거의 항상 "환자"지만, **명시하지 않으면 구현자가 매번 고민한다.**

| 대상 | 따르는 로케일 | 이유 |
|---|---|---|
| 환자 화면 문구 | **patient** | 환자가 읽는다 |
| TTS 음성·말속도 | **patient** | 환자가 듣는다 |
| 발음 채점기 선택 | **patient** | 환자가 말한다. 세션 시작 시 고정(§7-7 결정 B) |
| 문항 콘텐츠(단어·문장) | **patient** | 〃 |
| `qab_results.locale` | **patient** | 그 행을 만든 수행의 언어 |
| 보호자 대시보드·주간 리포트 | **caregiver** | 보호자가 읽는다 |
| 보호자 회고·알림 | **caregiver** | 〃 |
| 날짜·시각 표기 | **caregiver** | 보고서를 읽는 사람 기준 |
| 타임존·주 시작 요일 | **환자 `users` 행의 값 하나**(로케일과 별개, §13 OV-6·§14 1-3A) | 집계 버킷은 하나여야 한다(§3의 0-5) |

**타임존·주 시작 요일은 나누지 않는다.** 그건 언어가 아니라 **집계 축**이라,
둘로 나누면 같은 데이터가 두 가지로 집계된다.

### 0-4. 채점 경로의 `lang` 관통 (커밋 1개) — **영어판 게이트 뒤**(§14 D2-A)

> **정정(2026-09-06, /plan-eng-review)**: 이 항목은 원래 "자모 모듈 셋을
> `scorer[lang]` 인터페이스 뒤로 민다"였다. **그 모듈들은 프로덕션에서 안 돈다.**

`nameMatch.ts` · `speechScore.ts` · `phoneticDistance.ts`(합계 283줄)는
커밋 `17443af`(#15, 그림 이름대기를 발음 평가로 채점)에서 호출부가 끊겼다.
남은 import는 앞의 둘이 `phoneticDistance`를 부르는 것뿐 — **서로만 부르고
아무도 그들을 안 부른다.** 지금 테스트로만 살아 있다.

**실제로 도는 채점 경로 전부** (`pronunciationScore.ts:174-188`):

```
word     → azure.accuracyScore
sentence → round(accuracy*0.6 + completeness*0.4)
등급     → 90 / 75 / 60 / 40   (60 이상 정답)
```

한국어 특유 코드가 한 줄도 없다. Azure가 준 숫자에 가중치와 임계값을 걸 뿐이다.
`ai-service/routers/pronunciation.py:47`은 이미 `lang: str = Form("ko-KR")`이다.

**그래서 이 커밋이 할 일은 인터페이스가 아니라 관통이다:**

| | |
|---|---|
| `lang` | 프론트 → `/pronunciation`까지 관통(기본값 제거, §3의 0-3과 같은 작업) |
| 임계값 | `AZURE_GRADE_THRESHOLDS`(90/75/60/40)를 **로케일별 상수**로. 값은 Phase 2에서 보정 |
| 등급 문구 | `patientEncouragement` / `caregiverGradeLabel` / `UNSCORED_ENCOURAGEMENT` — 재구현(§7-7) |

**죽은 283줄은 이번 계획에서 다루지 않는다.** 지우는 판단은 자유 발화 STT 부채가
풀릴 때 다시 본다(문자열 거리가 그때 필요해질 수 있다) — 별도 TODO다.

### 0-5. 시간 축 — **가장 조용히 깨지는 것** (커밋 2개)

번역과 무관하다. 그래서 문자열 작업을 다 해도 남는다.

#### (a) 주 시작 요일이 월요일로 **양쪽에** 박혀 있다

| 층 | 파일 | 근거 |
|---|---|---|
| 백엔드 | `backend/src/quiz/quiz.service.ts:1520, 1538, 1541, 1543` | `date_trunc('week', …)` = Postgres **ISO 월요일 시작** |
| 프론트 | `frontend/src/memory-link/patient/domain/streak.ts` | `mondayOf()`, `WEEKDAY_LABELS = ['월','화',…,'일']` |

미국은 **일요일 시작**이 관습이다. 이건 라벨이 아니라 **집계 버킷**이라, 같은
데이터로 주간 리포트의 수치 자체가 달라진다. `streak.ts` 주석이 "월요일 시작
(getQabTrend의 주차 집계와 동일 규칙)"이라고 두 층의 일치를 명시해 두었는데,
로케일이 생기면 **그 규칙이 로케일별로 갈린다** — 일치 조건도 로케일별이 된다.

> **결정(2026-09-06)**: 주 시작 요일은 ~~환자 프로필에~~ **환자 `users` 행에 저장한다**(2026-09-12 정정, §13 OV-6). 로케일에서
> 파생하지 않는다 — `en-US`라도 사용자가 월요일 시작을 원할 수 있고, 무엇보다
> **집계가 서버에서 일어나므로 서버가 그 값을 알아야 한다.** 프론트의
> `mondayOf()`/`WEEKDAY_LABELS`와 백엔드의 `date_trunc('week')`이 **같은 저장값**을
> 읽게 만드는 것이 이 커밋의 합격 기준이다(지금은 둘 다 각자 월요일을 안다).

#### (b) 일·주 버킷이 **서버 세션 TimeZone**에 의존한다

```
backend/src/quiz/quiz.service.ts:1361      to_char(date_trunc('day', r.created_at), 'YYYY-MM-DD')
backend/src/practice/practice.service.ts:94  (동일)
```

`created_at`은 `timestamptz`라 `date_trunc`가 **서버 TZ로 해석**한다. 그런데
코드 어디에도 TZ 설정이 없다(환경 의존). 서버가 KST면 **미국 환자의 "오늘"이
KST 자정으로 잘린다** — 현지 오전 9시에 푼 문항이 전날로 집계된다.

M `align-timestamptz-and-indexes`(1784300000000) 주석이 남긴 교훈과 정확히
같은 계열이다: *"KST면 9시간 전체가 밀린다. `current_setting('TimeZone')`으로
해석해야 한다."*

> **결정(2026-09-06)**: **환자별 타임존을 ~~프로필에~~ 환자 `users` 행에 저장한다**(2026-09-12 정정). 아래 쓰기 경로(브라우저 추론·보호자 설정)는 **영어판 게이트 뒤**다(§14 1-3A) — 그전엔 기본값 `Asia/Seoul`.
> 최초값은 브라우저에서 추론하고(`Intl.DateTimeFormat().resolvedOptions().timeZone`),
> 보호자가 설정에서 바꿀 수 있게 노출한다. 집계 쿼리는 그 값으로 `AT TIME ZONE`을 건다.
>
> 매 요청마다 브라우저가 실어 보내는 방식은 **택하지 않았다** — 배치·주간 리포트처럼
> 요청이 없는 집계에서 기준이 사라지고, 기기를 바꾸면 값이 흔들린다.
> 로케일에서 파생하는 방식도 아니다 — 미국만 타임존이 넷 이상이고 이민자·여행 중
> 사용자가 틀린다.
>
> 스키마 변경이므로 **0-1의 `locale`, 위 (a)의 주 시작 요일과 한 마이그레이션에 묶는다.**

#### (c) "오늘"의 자가 두 개다

### 0-5b. 주 경계·타임존 계산을 함수 하나로 (커밋 1개)

> **결정(2026-09-06, /plan-eng-review)**: 경계 SQL을 만드는 헬퍼를 두고,
> 집계 쿼리 네 자리와 `where` 절이 **모두 그 하나를 쓴다.**

`AT TIME ZONE`을 거는 것만으로는 안 된다. `quiz.service.ts` 한 쿼리 안에
`date_trunc('week')`가 **네 번** 있고, 세 가지가 겹쳐 있다:

```
:1520  to_char(date_trunc('week', r.created_at), 'YYYY-MM-DD')      select
:1538  r.created_at >= date_trunc('week', now()) - make_interval(…)  where   ← 기준점이 다르다
:1541  .groupBy("date_trunc('week', r.created_at)")
:1543  .orderBy("date_trunc('week', r.created_at)", 'ASC')
```

1. **`date_trunc('week')`는 ISO 월요일 고정이다.** 타임존을 씌워도 월요일에
   잘린다. 일요일 시작은 **식 자체**를 바꿔야 한다(하루 밀어 자르고 되돌리기).
2. **`where`(:1538)는 `now()` 기준이다.** 버킷만 옮기고 창을 안 옮기면
   **첫 주와 마지막 주가 반쪽 데이터**가 된다.
3. **같은 식이 네 번 반복된다.** 넷 중 셋만 고쳐도 컴파일되고 테스트도 통과한다.

증상이 사나운 이유: **틀려도 숫자가 그럴듯하게 나온다.** 보호자는 그 숫자로
환자가 나아졌는지를 판단하는데, 틀렸다는 신호가 어디에도 안 뜬다.

`practice.service.ts:94`의 일 버킷도 같은 헬퍼를 쓴다.

> 새로 쓴다, 재사용 0%"라고 적혀 있었다. **그 셋은 프로덕션에서 안 돈다**(§3의 0-4).

> **재정정(2026-09-06, 외부 의견 수용)**: 이 절은 한 번 더 틀렸었다.
> "임계값 `90/75/60/40`은 한국어 데이터로 잡힌 값"이라고 적었는데 **아니다.**

`pronunciationScore.ts:157-161`이 출처를 명시한다:

> *"문자열 채점의 정답 경계(오류율 0.34 = 점수 66)보다 약간 더 관대하게 good
> 경계를 60으로 둔다. 완벽주의로 좌절시키지 않는 것이 재활 지속에 중요하다."*

**죽은 모듈의 경계에서 유비로 뽑은 둥근 수**다. 측정된 적이 없다. 그리고 근거로
걸었던 [등급 임계값 부채](20260816_speech_grade_threshold_debt.md)는 처음부터
끝까지 **문자열 채점기**(오류율 0.15/0.34) 문서라 Azure 임계값과 무관하다.

**그래서 Phase 2는 "보정"이 아니라 "없던 기준선을 처음 만드는 연구"였다.**
사용자 0명 시장에서 그걸 Phase 3 앞에 두는 건 순서가 거꾸로다.

> **결정(2026-09-06)**: **Phase 2를 별도 단계에서 내린다.** `en`은 `ko`와 **같은
> 임계값으로 열고**, accuracy 분포를 **로깅만** 한다. 재보정은 실사용자 표본이
> 쌓인 뒤의 **관측 항목**이다.

**외부 코퍼스로는 원리상 못 정한다.** 이 숫자가 재는 건 정답 여부가 아니라
**격려 곡선**이다(주석이 그렇게 말한다). UASpeech·TORGO는 마비말장애 코퍼스지
실어증이 아니고, 과제 형태도 다르며 DUA 승인이 필요하다 — 그걸로 이 앱의
격려 곡선을 정할 수는 없다.

| 남는 일 | 어디에 |
|---|---|
| `AZURE_GRADE_THRESHOLDS`를 로케일별 상수로(값은 당분간 동일) | §3의 0-4 |
| en-US accuracy 분포 로깅 | Phase 1에 얹는다 |
| 실사용 표본이 쌓이면 경계 재검토 | 관측 항목(§8-2) |

> **정정(2026-09-10)**: 아래 "선결 조건"은 Phase 2 삭제 전의 문장이다. 지금 결정은 위 인용의 "같은 임계값으로 열고 로깅만"이다 — 4기준 재측정은 선결 조건이 아니라 관측 항목이다.

**선결 조건 — 실측이 먼저다.** `acoustic-scorer-plan.md` §3의 4기준

### 2-2. 난이도 축 — 음절을 어떻게 셀 것인가

> **정정(2026-09-13, 영어 발화 문항 설계)**: 바로 아래 문장은 틀렸다. **단어 밴드만 음절이고, 문장 밴드는

> [20260913_EnglishSpeechContent_design.md](20260913_EnglishSpeechContent_design.md) §3.

`difficultyRules.ts`의 밴드가 전부 음절 수 기반이다(`repeatSpecForLevel`,
`readingRangeForLevel`, `syllableRangeForLevel`, `syllableCount`).
한국어는 `글자 수 = 음절 수`라 `syllableCount`가 한 줄이지만, **영어는 사전이 필요하다.**

> **결정(2026-09-06, 외부 의견으로 수정)**: **음절 수를 콘텐츠 JSON에 필드로 박는다.**
> 런타임에 세지 않는다.
>
> 처음엔 "CMUdict로 센다"였고 근거가 *"영어 채점기가 어차피 CMUdict를 쓰므로
> 자원을 공유한다"*였다. 그런데 **그 채점기는 없다**(§3의 0-4). 전제가 사라졌는데
> 결론만 남아 있었다.

> 필드를 같이 채우면 **런타임 사전도, 미등재어 폴백도, 그 폴백을 표시하는 장치도
> 전부 필요 없다.** §8-2의 7이 그대로 닫힌다.
>
> **단, 사람이 손으로 적으면 틀린다.** 생성 파이프라인이 자동으로 채우고
> (CMUdict를 **저작 도구로** 쓰는 건 무방하다), 검사가 값의 존재와 범위를 고정한다.
> 한국어판과 같은 축(음절)은 그대로 유지된다.
>
> 글자조합(`spell`)만은 예외다 — 철자 과제라 축이 다르다(§6-1).

## 6. 재설계 둘 — 무엇을 새로 만드는가

### 6-1. 글자조합(`spell`) — 영어엔 이 과제가 없다

지금: 정답 음절 타일 + 음운 유사 방해 타일을 눌러 낱말을 만든다.
난이도 축 셋 — 방해 타일 수(0·0·2·4·4) / 음절 범위 / 음운 유사 방해자
(`sharesInitialConsonant`, `sharesOnsetOrNucleus` — `shared/domain/korean.ts`).

영어 등가물은 **철자 타일(anagram)**인데, 그건 다른 과제다:
- 난이도 축이 글자 수·철자 규칙성이지 음절이 아니다
- 음운 유사 방해자가 성립하지 않는다(영어 철자는 소리와 1:1이 아니다)
- 임상적으로도 한국어의 음절 조합과 재는 것이 다르다

> **결정(2026-09-06)**: **철자 조합(anagram)으로 새로 설계한다.** 빼지 않는다.

**이 결정이 덜어주는 것.** `QAB_SUBTESTS`가 **8검사 그대로 간다.**
`Record<QabSubtest, string>`의 전수 강제도, 로케일별 검사 집합이라는 개념도
필요 없다 — Phase 0의 타입 작업이 그만큼 줄어든다.

**이 결정이 지우는 숙제.** Phase 3에 과제 설계가 하나 더 생긴다:

| 축 | 한국어(지금) | 영어(새로 정할 것) |
|---|---|---|
| 길이 | 음절 2~4 | **글자 수** (음절 축을 쓰지 않는 유일한 검사) |
| 방해 타일 수 | 0·0·2·4·4 | 그대로 옮길 수 있다 |
| 방해 타일의 질 | 음운 유사(초성/중성 공유) | **미정** — 영어 철자는 소리와 1:1이 아니라 등가물이 없다 |

세 번째 칸이 설계의 핵심이고, 지금 답하지 않는다(§8의 질문 5).
후보는 목표 단어에 없는 임의 글자 / 시각적 혼동 글자(b·d·p·q, m·n) /
목표 단어의 다른 순열을 만드는 글자이며, **셋이 재는 것이 서로 다르다.**

**그리고 이 검사가 무엇을 재는지 먼저 못 박아야 한다.** 철자 지식을 재게 되면
교육 수준이 언어 능력으로 잘못 읽힌다 — 한국어판이 `foil_kind='semantic'`을
거짓으로 찍었던 것과 같은 종류의 오염이다.

### 6-2. 문장이해 — 통사구조가 다르다

관계절 40 + 내포절 38 + 거울 26 + 생성 16 문항이 한국어 어순(SOV)과 조사에
기대어 가역성을 만든다. 영어(SVO, 어순 의존)에선 **같은 그림 쌍에 대해 난이도
구조가 달라진다.** 그림 자산은 100% 재사용되지만 문장은 처음부터 쓴다.
`QabItemBank.ts`에 박힌 "관계절이 놀고 있는 넷" 제외 목록도 영어에선 무의미하다.

### 6-3. 부수적: 한국어 전용 모듈 둘

- `shared/domain/korean.ts` — 조사 선택(`'칫솔'이에요` / `'사과'예요`).
  영어 대응은 a/an·복수형인데 **호출 시점이 다르다**(한국어는 낱말 뒤, 영어는 앞).
  문구 템플릿 구조가 바뀌므로 i18n 키 설계 때 같이 본다.
- `memory-link/shared/honorific.ts` — "어르신/여사님/어머니" 경칭 중복 회피.
  영어엔 대응 개념이 없다. **영어판에서는 통째로 비활성**이 맞다(빈 구현).

## 7. 화면·인증·운영 — 문자열 밖에서 더 계획할 것

§3~§6이 "검사와 채점"이라면 여기는 **그 바깥 전부**다. 하나씩은 작지만
빠뜨리면 출시가 막힌다.

### 7-0. 화면과 진입점 — 이 계획이 만드는 새 UI

> **결정(2026-09-06, /plan-design-review)**: 로케일은 **온보딩에서 묻는다.**
> 브라우저 추론값을 미리 고른 상태로 띄우고 보호자는 확인만 한다.

**왜 추론만으로는 안 되는가.** `navigator.language`는 언어+지역(`en-US`)을 주지만,
그건 **기기를 설정한 사람의 값**이다. 이 앱은 보호자가 자기 기기로 가입하고
`환자에게 건네기`(`CaregiverDashboard.tsx:160`)로 넘기는 구조라, 추론값은
**보호자용으로는 맞고 환자용으로는 틀릴 수 있다.**

| 상황 | `navigator.language` | 환자가 알아듣는 언어 |
|---|---|---|
| 서울 거주, 폰이 한국어 | `ko-KR` | 한국어 ✅ |
| LA 한인 어르신, 폰이 한국어 | `ko-KR` | 한국어 ✅ |
| **딸(영어 폰)이 어머니 대신 가입** | `en-US` | **한국어 ❌** |

세 번째 줄이 문제다. 틀린 언어는 불편이 아니라 **과제 수행 불가**이고, 실어증
환자는 그 이상함을 말로 알리기 어렵다. 게다가 §3의 0-5가 같은 자리의 값으로
집계 버킷을 가르므로 **주간 리포트 숫자까지 따라 틀린다.**

#### 진입점 둘

```
[최초]  보호자 가입 → 환자 프로필 만들기 → ★언어 설정 → 첫 세션
                                          └ 언어 · 타임존 · 주 시작 요일을 한 화면에서
                                            (§3의 0-1 마이그레이션 한 벌과 대응)

[변경]  보호자 대시보드 → 설정 → 언어·시간
                                └ §3의 0-5가 정한 자리. 그대로 둔다
```

#### 언어 설정 화면의 위계

한 화면 한 가지 일. 보호자가 보는 순서를 못 박는다.

| 순위 | 요소 | 사양 |
|---|---|---|
| 1 | 질문 제목 | h1 28px/700. "환자가 쓸 언어를 골라 주세요" — **환자의** 언어임을 문장에 박는다 |


**기본은 같다고 본다.** 대다수는 한 번만 답하고 끝나고, 다른 소수만 두 번째
화면을 본다. 브라우저 추론값은 **보호자 쪽**의 프리필로 쓰는 것이 맞다 —
그 값의 출처가 보호자 기기이기 때문이다.


### 7-1. 타이포그래피와 레이아웃

`DESIGN.md` 타이포 표의 역할이 **"한국어 전반 → Pretendard" 하나뿐**이다.
영어 스택 자체가 미정이다.

#### (a) 폰트 — **서체는 안 바꾼다. 받는 방식을 바꾼다**

> **결정(2026-09-06)**: `Pretendard`를 그대로 쓰고, CDN만
> `pretendard.css` → **`pretendard-dynamic-subset.css`**로 바꾼다.

실측 근거(2026-09-06, 브라우저 network 로그):

| | |
|---|---|
| 지금 CDN | `@font-face` 9개, **`unicode-range` 없음** = 라틴 전용 서브셋이 없다 |
| 실제 전송량 | Regular 767KB + Bold 792KB + SemiBold 787KB = **약 2.3MB** |
| 그 대가 | **영어만 읽는 사용자도 한글 1만여 자를 통째로 받는다** |
| 대안 | 같은 저장소의 `pretendard-dynamic-subset.css`는 `@font-face` 828개가 전부 `unicode-range`로 갈려 있다 |
| **교체 후 실측** | woff2 19조각 **235KB** + CSS **22KB** = **257KB** — **약 89% 감소** |

**서체를 바꾸지 않는 이유가 둘이다.**

1. **화면이 1px도 안 바뀐다.** 같은 글리프를 조각으로 나눠 담은 파일이라,
   아래 (b)의 팽창 수치가 그대로 유효하다. 서체를 바꾸면 **다시 재야 한다.**
2. **Pretendard의 라틴은 이미 좋다.** 캔버스 실측으로 확인했다 —
   Pretendard와 Inter는 x-height 9px·cap-height 12px로 **세로 비례가 동일**하고
   가로만 Inter가 3.7% 넓다(라틴 글리프가 Inter 파생이라는 통설이 수치로 확인된다).
   새 서체를 들이면 브랜드 결정이 하나 늘고 두 언어 화면이 미묘하게 갈린다.

| 서체 | "Hand the device to the patient" 폭 | x-height | cap-height |
|---|---:|---:|---:|
| **Pretendard** | 223.4px | 9px | 12px |
| Inter | 231.7px (+3.7%) | 9px | 12px |
| Source Sans 3 | 206.8px (−7.4%) | **8px** | **11px** |

Source Sans 3는 같은 16px에서 소문자가 1px 작다 — 고령 사용자 대상에선 그냥 손해다.

**덤**: 한국어판 첫 로딩도 같이 빨라진다. 지금은 한국 사용자도 안 쓰는 글자까지 받는다.

숫자 폰트(Geist + `tnum`)는 **그대로 간다.**

#### (c) `word-break` — TODO-008이 영어로 되돌아온다

`index.css:136-137`의 전역 규칙:

```css
word-break: keep-all;      /* 한국어 어절 보존 */
overflow-wrap: anywhere;   /* 가로 오버플로 방지 */
```

이건 **TODO-008**(2026-08-02, c747556)의 수정이다 — 375px에서 「환자 정 / 보」,
「로그아 / 웃」처럼 단어 중간이 끊기던 것을 고쳤다.

**`keep-all`은 한국어 규칙이다.** 영어에선 아무 일도 하지 않는다(영어는 원래
공백에서 끊긴다). 남는 건 `overflow-wrap: anywhere` 하나이고, 그건 **영어 단어를
글자 단위로 쪼갠다** — 같은 헤더 버튼에서 「Patient informat / ion」이 된다.

세션 학습 `break-keep-vs-overflow-wrap-anywhere`가 남긴 교훈이 여기 그대로다:
*"word-break만 손보면 소용없다 — overflow-wrap:anywhere가 그 위에서 강제로
다시 쪼갠다. 진짜 원인은 대개 레이아웃(칸 폭 부족)이다."*

**해야 할 것** — 전역 한 벌을 로케일별로 가른다:

| | ko | en |
|---|---|---|
| `word-break` | `keep-all` (유지) | `normal` |
| `overflow-wrap` | `anywhere` (URL 안전망) | `break-word` — **단어를 통째로 다음 줄로 내리고, 그래도 안 되면 그때만 쪼갠다** |
| `hyphens` | 해당 없음 | `auto` 검토 (긴 단어의 가독성) |

**그러나 위 학습이 경고한 대로, 이건 대증요법이다.** 헤더가 375px를 9px 넘긴
진짜 원인은 줄바꿈 속성이 아니라 **칸 폭 부족**이다 — 아래 (d)가 그걸 다룬다.

### 7-4. 콘텐츠 문화 적합성 — 번역이 아니라 **항목 교체** 판단

그림 167개가 영어 slug라 기술적으로는 100% 재사용된다. 그러나 **우체통·이불처럼
한국 생활에 맞춰 고른 항목**은 미국 사용자에게 어색하거나 덜 익숙할 수 있다.
이건 라벨을 갈아서 되는 일이 아니라 **항목을 빼고 다른 것을 넣는 일**이다.

**산출물**: 167개를 훑어 교체 후보를 표시한 목록. `namingPhotos`의 실물 사진도
같은 검수를 받는다. 이 검수 없이 라벨만 번역하면, 단어이해 정답률이 언어 능력이
아니라 **문화 친숙도**를 재게 된다 — QAB 점수의 뜻이 조용히 바뀐다.

정적 TTS도 여기 딸린다: `scripts/generate-static-tts.mjs`가 한국어 텍스트를 키로
쓰므로 언어별 매니페스트로 가르고 정적 오디오 34개를 재생성한다.

### 7-5b. 이번 리뷰가 정한 테스트 요구 (2026-09-06, /plan-eng-review)

### 7-5. 테스트 전략 — 지금 계획의 가장 큰 구멍

테스트가 한국어 자산에 묶여 있다(`QabItemBank.test.ts` 98개,
`speechScoreGolden.test.ts`, `wordCompAssets.test.ts` 등). 로케일이 생기면
**어떤 테스트가 언어별로 두 벌이 되고 어떤 게 공유인지**를 정해야 한다.

정하지 않으면 둘 중 하나가 된다:
- 테스트가 무한 증식한다(모든 케이스 × 언어 수)
- **영어 경로가 무검증으로 남는다** ← 이쪽이 훨씬 위험하다

**분류 기준 초안**: 로직 불변식(밴드 크기, itemId 중복 없음, 라벨 전수)은 **공유**
— 언어별 데이터를 주입해 같은 테스트를 돌린다. 음운·문구에 의존하는 것
(골든 채점, 조사 선택, 단서 문구)은 **언어별 두 벌**.

### 7-6. 로케일 결정 경로

> **결정(2026-09-06)**: **계정 속성이 우선이다.** 로케일은 환자 프로필에 저장하고
> (§3의 0-1), 로그인 전 화면만 브라우저 언어로 고른다.

타임존·주 시작 요일이 이미 같은 자리에 들어가므로(§3의 0-5) **시간과 언어가
한 곳에서 온다.** 라우팅·공유 링크·보호자↔환자 연결 링크 구조를 건드리지 않는 것도
이 방식의 이점이다.

URL 접두(`/en/`)는 택하지 않았다 — 라우팅 전면 변경이 필요하고, 계정 로케일과
URL이 어긋날 때 무엇이 이기는지 규칙을 따로 세워야 한다. 도메인 분리도 아니다
(인프라·쿠키·인증 도메인 비용이 지금 단계엔 과하다). **SEO는 포기한다** —
로그인 뒤에서 쓰는 앱이라 잃을 것이 없다.

**보호자와 환자의 로케일은 다를 수 있다(2026-09-06 결정).** 둘로 나눠 저장하고,
어느 기능이 어느 쪽을 따르는지는 §3의 0-1의 표가 정본이다.

### 7-7. 상태 표 — 영어판에만 존재하는 상태

> **결정 A(2026-09-06, 외부 의견으로 수정)**: 게이트를 **로케일 필드별로 나눈다.**

> | `caregiver_locale='en-US'` | **UI 문자열 + 보호자용 시드**(치유 메시지·일기 질문)가 차면 연다 — 문항 풀을 기다리지 않는다 |

> 바로 그 사용자**(영어 보호자 + 한국어 부모, §3의 0-1)를 Phase 3 끝까지 막는다.

> **결정 B(2026-09-06)**: **로케일은 세션 시작 시점에 고정한다.**
> `qab_results.locale`(§3의 0-1)에 그 고정값을 쓴다. 세션 중 설정에서 바꾸면
> "다음 연습부터 적용됩니다"로 안내하고, 진행 중인 세션은 건드리지 않는다.

**결정 A의 이유.** react-i18next의 기본 폴백은 원문 노출이고, 여기서 원문은
한국어다. 그대로 두면 미국 고령 환자 화면에 "따라 말해 보세요"가 뜬다.
일반 앱이면 "번역이 덜 됐네"로 끝나지만, **실어증 환자는 읽혀야 할 글을 못 읽는
것을 자기 증상으로 받아들일 수 있다.** 재활 앱에서 그건 단순한 버그가 아니다.

**결정 A의 대가(받아들인 것).** Phase 1~2 동안 영어 경로를 실제로 실행해 볼 수
없다. 내부 QA 우회를 둘 것인지는 §8-2의 열린 질문으로 남긴다 — 두더라도
프로덕션 빌드에서 강제로 꺼지는 형태여야 한다(`CryptoService`의 fail-closed
패턴이 이 저장소의 선례다).

> **정정(2026-09-10, CEO 리뷰 외부 의견)**: 아래 "채점기가 다르다(자모 분해 vs CMUdict)"는 낡은 근거다 — 두 언어 모두 Azure accuracy 한 자로 잰다(§3의 0-4). **결정 B는 그대로 유효하다.** 실제 근거는 문항 풀·TTS 음성·`manifest_version`·음절 밴드가 로케일별이라는 것 — 세션 중 로케일이 바뀌면 한 회차가 두 풀의 문항으로 섞이고, 점수 추세가 다른 모집단을 합친다.

**결정 B의 이유.** 한국어와 영어는 **채점기가 다르다**(자모 분해 vs CMUdict 음소,
§5의 2-1). 한 세션에 둘이 섞이면 그 회차 점수는 두 개의 다른 자로 재서 합산한
값이 된다. `pronunciationScore.ts` 머리말이 문자열 폴백을 금지한 것과 **같은
종류의 오염**이다 — 자가 바뀌면 회차 간 비교가 무너진다.

### 16-3. 이 줄 세우기가 드러낸 것 — 기존 목록과 다른 셋

**① T7은 M2가 아니라 M1을 막는다.** §13-8은 T7을 "영어판(게이트 통과 뒤)" 목록에 두고 조건을 "미국 첫
가입 전"이라 적었다. 그런데 결정 A로 보호자 문이 M1에 먼저 열리고, 영어 보호자는 대부분 미국에 산다 —
**보호자 `en-US`를 여는 커밋이 사실상 첫 미국 가입을 허용하는 커밋이다.** 성인 환자 대리 동의, MHMDA,
US 로케일 발화 보존 기본 끔, CCPA 권리·영문 약관까지 M1 Exit 전에 끝나야 한다. 법률 확인은 리드타임이
있으니 M0에서 시작한다.

**② 0-5c는 "게이트 뒤"가 아니라 M1의 맨 앞이다.** §14 D2-A가 0-5c를 "코드 기본값이라 나중에 해도 비용이
같다" 쪽에 넣었다. 쓰기 경로가 없는 동안은 맞다. 하지만 M1 ④가 언어 설정 화면을 만드는 순간 게이트 없는
문이 생긴다. 그래서 순서는 **서버 거부 → 설정 화면 → 목록에 값 추가**다. 이렇게 두면 문 열기가 한 줄
설정 변경이 되고, 되돌리기도 한 줄이다.

**③ M2의 콘텐츠 작성은 M1을 기다리지 않는다.** 문항 JSON은 i18n 스택과 무관하다. 임계 경로가 검수(§13,
§10)이므로 **M0 판정 직후 M1과 병렬로 시작해야** 전체 일정이 콘텐츠 한 줄로 늘어지지 않는다. M2 문만 두
줄(M1 완료 + 콘텐츠 기준 충족)을 모두 기다린다.
