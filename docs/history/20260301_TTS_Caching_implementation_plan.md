# TTS 음성 캐싱 및 리소스 최적화 아키텍처

## 1. 개요 (Goal Description)
자주 반복되는 실어증 평가 지시문 및 고정된 평가 단어들에 대해 매번 TTS(Text-to-Speech) 실시간 생성을 수행할 경우, 다음과 같은 문제점이 발생합니다.
- 외부 API 호출에 따른 막대한 비용 (API Cost)
- 네트워크 지연으로 인한 사용자 대기 시간 증가 (High Latency)
- 앱/디바이스의 불필요한 네트워크 대역폭 및 배터리 자원 소모

본 문서에서는 이를 해결하기 위해 **정적 파일 사전 생성(Pre-generation)** 과 **동적 해시 기반 캐싱(Dynamic Hash Caching)** 을 결합한 **하이브리드 TTS 파이프라인 아키텍처** 구현 계획을 제안합니다.

---

## 2. 하이브리드 아키텍처 제안

전체 음성 데이터를 두 가지 유형으로 분류하여 최적화된 방법으로 처리합니다.

### 2.1. 정적 음성 에셋 (Pre-generated Static Audio)
"화면을 눌러주세요", "다음 중 단어와 일치하는 그림을 고르세요" 등 평가 과정의 UI 안내 및 공통 지시문은 내용이 변경되지 않습니다.

- **방식**: 개발 및 배포 전, 고품질 TTS(ex. ElevenLabs, Google Cloud TTS)를 사용해 오디오 파일(mp3, wav)로 일괄 생성합니다.
- **저장 위치**: 클라이언트 앱 내의 정적 에셋 폴더(`assets/audio/common/`)에 포함시키거나, 빠르고 캐시 적용이 쉬운 CDN(Content Delivery Network)을 통해 배포합니다.
- **장점**: 런타임에 외부 연동이 전혀 필요 없어 빠르고, API 과금 비용이 0원이며, 오프라인(로컬 에셋의 경우) 환경에서도 작동합니다.

### 2.2. 동적 생성 음성 (Dynamic Hash Caching)
사용자별 특화된 문장이나 LLM에 의해 런타임에 동적으로 새롭게 출제되는 문항 등 사전 생성이 불가능한 텍스트에만 제한적으로 적용합니다.

- **방식**: 
  1. 클라이언트(프론트엔드)가 백엔드에 TTS 생성을 요청할 때, 재생해야 할 텍스트를 전송합니다.
  2. 백엔드는 해당 텍스트를 기반으로 고유한 해시값(예: SHA-256)을 생성합니다. (예: `hash("오늘 날씨는 맑습니다") = a1b2c3d4`)
  3. 백엔드는 자신의 로컬 스토리지, Redis 또는 S3 캐시에 해당 해시값을 파일명으로 갖는 오디오 파일이 존재하는지 검사합니다.
     - **Cache Hit(존재함):** 즉시 해당 파일의 다운로드 URL을 프론트엔드에 응답합니다. (TTS API 호출 생략)
     - **Cache Miss(존재하지 않음):** 외부 TTS API에 텍스트를 전송하여 오디오 스트림을 받아오고, 이를 서버 스토리지에 해시값 파일명으로 저장한 후 클라이언트로 반환합니다.

### 2.3. 클라이언트 내장 Web Speech API (Fallback / Optional)
네트워크가 끊기거나 외부 API 서비스에 장애가 발생한 상황에 대비하여, 기존 `LOC` 진행 시 구현했던 브라우저 및 디바이스 내장의 `window.speechSynthesis`를 Fallback으로 최하단에 둡니다.

## 3. 관련 컴포넌트 구조 변경 기획

### [Component: Backend TTS Pipeline]

#### [NEW] `src/backend/services/tts_service.py` 또는 유사한 백엔드 계층
- 입력 텍스트 문자열에 대한 정규화(공백 제거, 특수문자 처리) 및 해시 생성 함수
- 클라우드 스토리지(S3 등) 또는 로컬 파일 시스템 내 캐시 폴더 접근 로직
- Cache Miss 일 때 외부 TTS Provider를 호출하는 로직

### [Component: Frontend Audio Handling]

#### [NEW] `src/frontend/hooks/useDynamicAudio.ts`
- 서버에 텍스트를 전송하고 오디오 URL을 비동기로 받아오는 커스텀 React/React Native Hook.
- (선택 사항) 브라우저 수준에서의 캐싱(Service Worker 등)을 통해 한 세션 내에서 같은 텍스트가 여러 번 트리거될 때 백엔드 통신마저 생략하도록 구성.

#### [MODIFY] 기존 검사 화면(`WordComp`, `SentComp`, `LOC` 등)
- 고정된 지시문을 재생하는 부분은 외부 TTS 호출을 제거하고, `<audio src="/assets/audio/common/instruction_01.mp3">` 형태(또는 네이티브 Audio 객체)로 대체합니다.
- 동적 텍스트가 필요한 부분은 새롭게 구현된 `useDynamicAudio` hook이나 백엔드 캐시 레이어를 호출하도록 변경합니다.

## 4. 기대 효과 (Impact)
1. **비용 절감**: TTS API 요금을 혁신적으로(최대 90% 이상) 절약할 수 있습니다.
2. **반응성 개선**: 캐시된 음성의 즉각적인 반환(수십 ms 이내)으로 지연 없는 UX를 달성합니다.
3. **확장성**: 사용자, 문항, 평가 세션이 크게 늘어나도 해시 기반 캐싱 파일이 어느 정도 구축되면 일종의 자산(Asset)으로 쌓여 성능과 비용 면에서 더욱 강점을 가집니다.
