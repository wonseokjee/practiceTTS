# Phase 4 — 텔레포니 (3주) ★ 차별화 지점

**목표**: 실제 전화번호로 걸면 AI가 받아 대화하는 시스템을 만든다.

**왜 차별화되는가**: 음성 AI 지원자 대부분이 브라우저 데모에서 멈춥니다. 전화망은
브라우저와 규격 자체가 달라서(8kHz, µ-law, RTP), 여기서 겪는 문제들은 검색으로
미리 알기 어렵습니다. 굴려본 사람만 아는 영역입니다.

---

## 4-1. WebRTC (5일)

### 시그널링과 미디어의 분리

WebRTC를 처음 배울 때 가장 헷갈리는 지점입니다.

```
        ┌── 시그널링 (WebSocket 등, 내가 직접 구현) ──┐
브라우저 A                                          브라우저 B
        └──────── 미디어 (RTP/SRTP, P2P) ───────────┘
```

**WebRTC 표준은 미디어만 정의합니다.** SDP를 어떻게 주고받을지는 표준에 없어서
개발자가 직접 만들어야 합니다. "WebRTC 연결이 안 된다"의 절반은 시그널링 문제입니다.

### SDP offer/answer

```
A: createOffer()      → SDP(내 코덱 목록, 내 후보 주소) → 시그널링 → B
B: setRemoteDescription(offer)
B: createAnswer()     → SDP(합의된 코덱) → 시그널링 → A
A: setRemoteDescription(answer)
→ ICE 후보 교환 → 연결
```

### ICE / STUN / TURN — NAT 뒤에서 연결되는 이유

| | 역할 | 비용 |
|---|---|---|
| **STUN** | "내 공인 IP가 뭐야?"를 알려주는 서버 | 저렴 (질의 한 번) |
| **TURN** | 직결 실패 시 미디어를 중계 | 비쌈 (트래픽 전량 통과) |
| **ICE** | 여러 후보 경로를 시도해 최적 경로 선택 | — |

**실무 함정**: 개발 중엔 STUN만으로 잘 되다가, 기업 방화벽 뒤 사용자에게서 갑자기
실패합니다. Symmetric NAT나 UDP 차단 환경에서는 TURN이 필수입니다.
"프로덕션에 TURN 서버를 준비했는가"는 실전 경험을 가르는 질문입니다.

### RTP / 코덱 / jitter buffer

- **RTP** — 실시간 미디어 전송. UDP 위에서 순서 번호와 타임스탬프를 붙임
- **Opus** — WebRTC 기본 코덱. 8~48kHz 가변, 대역폭 적응
- **Jitter buffer** — 패킷 도착 간격이 들쭉날쭉한 걸 흡수. 크면 안정적이지만 지연 증가
- **PLC(패킷 손실 은닉)** — 잃은 패킷 구간을 추정해 메움

> **지연 관점**: jitter buffer는 Phase 3 예산표의 "네트워크·버퍼링 100ms"에
> 해당합니다. 이걸 줄이면 지연은 좋아지지만 음질이 깨집니다. 트레이드오프를
> 이해하고 있다는 것 자체가 신호입니다.

## 4-2. SIP / VoIP (5일)

### 기본 호 흐름

```
발신자                          수신자
  │──────── INVITE ───────────▶│   "통화 걸겠습니다" (SDP 포함)
  │◀─────── 100 Trying ────────│   "받았어요"
  │◀─────── 180 Ringing ───────│   "벨 울리는 중"
  │◀─────── 200 OK ────────────│   "받았습니다" (SDP 응답)
  │──────── ACK ──────────────▶│   "연결 확인"
  │                            │
  │═══════ RTP 미디어 ════════▶│   ← 실제 음성은 여기로 (SIP 아님)
  │                            │
  │──────── BYE ──────────────▶│   "끊겠습니다"
  │◀─────── 200 OK ────────────│
```

**핵심 통찰**: SIP은 시그널링만 합니다. 음성은 RTP로 별도 경로를 탑니다.
WebRTC의 시그널링/미디어 분리와 정확히 같은 구조입니다.

### 알아야 할 용어

| 용어 | 뜻 |
|---|---|
| **SIP trunk** | 전화망과 내 시스템을 잇는 회선. 번호를 여기에 붙임 |
| **REGISTER** | 단말이 "나 여기 있어요"를 등록 |
| **B2BUA** | 양쪽 호를 각각 종단하며 중계하는 구조. AI 에이전트가 여기 해당 |
| **DTMF (RFC 2833)** | "1번을 눌러주세요". 오디오가 아니라 RTP 이벤트로 전달 |

### ★ G.711 µ-law, 8kHz — 반드시 이해할 것

**전화망 오디오는 8kHz 샘플레이트, µ-law 압축, 모노입니다.**

이것이 왜 중요한가:

1. **STT 정확도가 떨어집니다.** 대부분의 STT 모델은 16kHz 이상으로 학습됩니다.
   8kHz에서는 마찰음(ㅅ, ㅆ, ㅎ)과 파열음 구분이 어려워집니다. 브라우저 데모에서
   95%였던 정확도가 전화에서 85%로 떨어지는 흔한 이유입니다.
2. **나이퀴스트 한계로 4kHz 이상 주파수가 통째로 사라집니다.** 업샘플링해도
   복원되지 않습니다 — 없는 정보를 만들 수는 없습니다.
3. **TTS도 영향받습니다.** 24kHz로 생성한 고품질 음성을 8kHz로 다운샘플링하면
   전화 특유의 먹먹한 소리가 됩니다.

**대응 방법:**

- 전화 오디오로 파인튜닝된 STT 모델 선택 (여러 벤더가 telephony 모델을 별도 제공)
- 도메인 어휘 힌트/부스팅 제공 (예약 시스템이면 메뉴명·지역명)
- 중요 정보(전화번호, 예약번호)는 **DTMF 입력으로 우회**
- 확인 질문으로 보정: "010-1234-5678 맞으실까요?"

> **면접 예상 질문**: "전화망에서 STT 정확도가 떨어지는데 어떻게 대응하나요?"
> 위 네 가지를 순서대로 말할 수 있으면 이 주제는 통과입니다.

### Asterisk / FreeSWITCH를 한 번은 띄워볼 것

실무에서 안 쓰더라도 **SIP을 몸으로 이해하는 데 최고의 도구**입니다.

```
# Asterisk 최소 실습
1. 도커로 Asterisk 기동
2. 소프트폰(Zoiper, Linphone) 2대를 extension 1001, 1002로 등록
3. 1001 → 1002 통화
4. tcpdump/Wireshark로 INVITE → 200 OK → RTP 흐름 관찰
```

Wireshark에서 SIP 패킷을 직접 보는 경험이 이 phase의 분기점입니다.

## 4-3. 클라우드 경로 — 실제 데모 만들기 (5일)

### Twilio Voice + Media Streams — 가장 빠른 길

전화 오디오를 **WebSocket으로 그대로** 받습니다.

```xml
<!-- 전화가 오면 Twilio가 이 TwiML을 요청 -->
<Response>
  <Connect>
    <Stream url="wss://myserver.example.com/media" />
  </Connect>
</Response>
```

WebSocket으로 오는 이벤트:

```jsonc
{ "event": "connected" }
{ "event": "start", "start": { "streamSid": "MZ...", "callSid": "CA..." } }
{ "event": "media", "media": {
    "timestamp": "1240",
    "payload": "<base64 µ-law 8kHz, 20ms(160바이트) 프레임>"
}}
{ "event": "stop" }
```

봇이 말하려면 같은 형식으로 되돌려 보냅니다.

```ts
ws.send(JSON.stringify({
  event: 'media',
  streamSid,
  media: { payload: base64MulawChunk },
}))

// ★ barge-in의 핵심: 이미 보낸 오디오 버퍼를 비운다
ws.send(JSON.stringify({ event: 'clear', streamSid }))
```

> **`clear` 이벤트가 Phase 3에서 배운 "이미 전송된 버퍼 폐기"의 실체입니다.**
> 이걸 안 보내면 사용자가 끼어들어도 봇이 몇 초 더 떠듭니다. 전화 데모에서 가장
> 자주 나오는 버그이고, 원인을 아는 사람은 드뭅니다.

`mark` 이벤트로 "어디까지 재생됐는지"를 추적할 수 있습니다. Phase 3의
"실제 재생된 부분까지만 대화 기록에 남기기"가 여기서 구현됩니다.

### LiveKit SIP

SIP trunk를 LiveKit room에 연결. Phase 3에서 LiveKit Agents로 만들었다면
전화 연동이 설정 수준으로 끝납니다.

### 그 외 다뤄볼 것

- **아웃바운드 발신** — 인바운드보다 규제가 훨씬 까다롭습니다(수신 거부 목록,
  발신 시간대 제한, 자동 발신 고지 의무)
- **통화 녹취** — 저장 위치, 보존 기간, 고지 의무
- **상담원 전환** — Phase 5에서 자세히

## 실습 과제

### ★ 전화 받는 AI (이 커리큘럼의 핵심 산출물)

1. Twilio에서 전화번호를 하나 산다 (한국 번호는 절차가 복잡하니 미국 번호로 시작)
2. 인바운드 웹훅 → TwiML `<Stream>` → 내 WebSocket 서버
3. µ-law 8kHz ↔ 파이프라인 샘플레이트 변환을 구현한다
4. Phase 3의 파이프라인을 연결한다
5. **barge-in이 전화에서도 동작하게 만든다** (`clear` 이벤트)
6. Phase 2의 지연 계기판을 붙여 **브라우저 대비 몇 ms 늘었는지** 측정한다

### 측정하고 기록할 것

| 항목 | 브라우저 | 전화 | 차이 |
|---|---|---|---|
| 총 턴 지연 p95 | | | |
| STT 단어 정확도 | | | |
| barge-in 반응 시간 | | | |

**이 표가 면접에서 가장 강력한 자료입니다.** 대부분의 지원자는 브라우저 숫자만
가지고 있습니다.

### 보너스

- DTMF 입력 처리 (전화번호를 키패드로 받기)
- 통화 중 무음 20초 → 자동 종료
- 통화 녹취 저장 후 Phase 2 trace에 링크

## 자가진단

- [ ] SDP offer/answer 흐름을 그림 없이 설명할 수 있다
- [ ] TURN이 필요한 네트워크 상황을 구체적으로 말할 수 있다
- [ ] SIP INVITE부터 BYE까지의 메시지 흐름을 순서대로 안다
- [ ] SIP과 RTP가 왜 분리되어 있는지 설명할 수 있다
- [ ] 전화망이 8kHz인 것이 STT에 미치는 영향을 설명할 수 있고, 대응책을 4가지 안다
- [ ] Twilio Media Streams의 `clear` 이벤트가 왜 필요한지 안다
- [ ] Wireshark로 SIP 패킷을 직접 본 적이 있다
- [ ] 실제 전화번호로 걸리는 데모를 가지고 있다
