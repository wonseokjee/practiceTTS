# Phase 7 — 프로덕션 & 0-1 도입 (2주)

**목표**: 만든 것을 팔 수 있는 상태로 만든다. 평가 하네스, 안정성 장치,
비용 모델, 파일럿 제안서.

---

## 7-1. 평가 하네스 (4일)

**음성은 수동 테스트가 지속 불가능합니다.** 프롬프트 한 줄 바꿀 때마다 전화 20통을
직접 걸 수는 없습니다. 자동화가 필수입니다.

### 골든셋 설계

시나리오를 5개 축으로 나눕니다.

| 축 | 예시 |
|---|---|
| **정상** | "내일 저녁 7시 4명 예약해주세요" |
| **말 끊김·재시작** | "다음 주 화요일... 아니 수요일로 해주세요" |
| **잡음·저음질** | 카페 배경음, 전화망 8kHz 열화 |
| **사투리·비표준 발화** | 지역 억양, 빠른 발화, 노년층 발화 |
| **악의적·경계 입력** | 프롬프트 인젝션, 무한 반복 유도, 상담원 요구 |

각 항목에 **기대 결과**를 명시합니다.

```yaml
- id: interrupt-and-correct
  audio: fixtures/interrupt_correct_ko.wav
  expect:
    intent: 예약
    date: "2026-08-05"      # 정정된 수요일
    escalated: false
    max_turn_latency_ms: 1200
```

### 합성 발화 주입

```python
async def replay_call(fixture):
    """실제 전화 대신 오디오 파일을 파이프라인에 주입"""
    call = await pipeline.start_synthetic_call()
    for chunk in read_mulaw_frames(fixture.audio, frame_ms=20):
        await call.push_audio(chunk)
        await asyncio.sleep(0.02)          # 실시간 속도로 재생
    return await call.finish()
```

**실시간 속도로 재생하는 것이 중요합니다.** 오디오를 한꺼번에 밀어넣으면 VAD와
turn detection이 전혀 다르게 동작해서 테스트 의미가 없어집니다.

### CI 연결

```
PR 생성
  → 골든셋 40건 재생
  → Langfuse dataset run으로 점수 기록
  → 기준 미달이면 머지 차단
```

Phase 2에서 만든 Langfuse dataset이 여기서 회수됩니다.

## 7-2. 안정성 장치 (3일)

| 장치 | 왜 | 구현 |
|---|---|---|
| **최대 턴 수** | 봇이 무한 루프에 빠지면 통화비만 나감 | 20턴 초과 시 상담원 이관 |
| **루프 감지** | 같은 질문 반복 | 최근 3턴 유사도가 높으면 이관 |
| **통화 타임아웃** | 방치된 통화 | 10분 초과 시 종료 안내 후 끊기 |
| **무음 타임아웃** | 사용자가 자리를 비움 | 20초 무음 → 확인 → 30초 → 종료 |
| **폴백 체인** | STT/LLM/TTS 벤더 장애 | 2차 벤더로 자동 전환 |
| **서킷 브레이커** | 다운스트림 API 연쇄 장애 | 실패율 임계 초과 시 즉시 이관 모드 |

### 부하 테스트

동시 통화 N개에서 지연이 어떻게 무너지는지 측정합니다.

```
동시 통화   1    5   10   20   50
p95 지연  820  850  910 1240 3100ms
                          ↑ 여기서 무너짐
```

**무너지는 지점을 아는 것 자체가 자산입니다.** "동시 20통까지는 SLA를 지킵니다"라고
말할 수 있는 것과 "잘 됩니다"의 차이입니다.

## 7-3. 비용 모델링 (2일)

### 분당 원가 분해

```
STT       스트리밍 인식           $0.004~0.010 / 분
LLM       입력+출력 토큰          아래 계산 참조
TTS       생성 문자 수            $0.004~0.020 / 분
텔레포니   회선 + 번호             $0.008~0.015 / 분
인프라     서버·TURN·저장          $0.002 / 분
────────────────────────────────────────────
합계                              대략 $0.03~0.06 / 분
```

### LLM 비용 계산 예시 (2026-07 기준 단가)

3분 통화, 12턴, 턴당 입력 1,500토큰(누적 컨텍스트 포함) / 출력 120토큰:

```
입력  12 × 1,500 = 18,000 토큰
출력  12 ×   120 =  1,440 토큰

claude-sonnet-5 ($3 / $15 per 1M)
  입력  18,000 / 1M × $3  = $0.054
  출력   1,440 / 1M × $15 = $0.022
  합계 ≈ $0.076 / 통화 (약 100원)
```

**프롬프트 캐싱을 적용하면 시스템 프롬프트 부분이 대폭 저렴해집니다.** 매 턴 같은
지시문을 반복 전송하는 음성 에이전트는 캐싱 효과가 특히 큽니다. 캐시 읽기는 기본
입력가의 약 1/10 수준입니다.

> **모델 선택은 비용만으로 정하지 마세요.** 실시간 대화는 TTFT가 지연 예산을
> 지배합니다. 저렴한 모델이 느리면 사용자 경험이 무너져서 결국 봉쇄율이 떨어지고
> ROI가 나빠집니다. 항상 **지연·품질·비용 3축**으로 봅니다.

### 상담원 인건비와 비교

```
상담원 시급 12,000원, 평균 처리 3분 → 건당 600원
봇 건당 원가 (3분 통화) ≈ 200원

봉쇄율 30%, 월 10,000건:
  절감  3,000건 × 600원 = 1,800,000원
  비용 10,000건 × 200원 = 2,000,000원  ← 전체 통화가 봇을 거침
  ────────────────────────────────
  손익 = -200,000원  ← 봉쇄율 30%로는 적자!
```

**이 계산이 중요합니다.** 봇이 전체 통화를 받으면서 30%만 해결하면 오히려 손해일
수 있습니다. 손익분기 봉쇄율을 계산하고, 그 위에서 파일럿 목표를 잡아야 합니다.
(위 예시의 손익분기는 약 33%.)

## 7-4. 0-1 파일럿 설계 (3일)

### 파일럿 설계 원칙

| 원칙 | 나쁜 예 | 좋은 예 |
|---|---|---|
| **범위를 좁게** | "고객 문의 전반" | "예약 변경 문의만" |
| **성공 기준을 숫자로** | "고객 만족도 개선" | "봉쇄율 40%, CSAT 유지" |
| **기간을 짧게** | "6개월 도입" | "4주 파일럿 후 결정" |
| **비교군 확보** | 그냥 켜기 | 50% 트래픽만 라우팅 |
| **롤백 경로** | 없음 | 스위치 하나로 전량 상담원 |

**단일 인텐트로 시작하세요.** "예약 변경"만 처리하는 봇이 90% 봉쇄율을 내는 것이,
모든 걸 처리하며 30%를 내는 것보다 훨씬 좋은 파일럿입니다. 확장은 그 다음입니다.

### 제안서 1페이저 구조

```
1. 현황     월 통화량, 현재 AHT, 현재 포기율, 인력 규모
2. 범위     "예약 변경 인바운드 통화만" — 전체의 약 25%
3. 목표     봉쇄율 40% / CSAT 현행 유지 / AHT 20% 감소
4. 기간     4주 (1주 셋업, 2주 운영, 1주 분석)
5. 측정     A/B 50:50 분할, 주간 리포트
6. 리스크   STT 정확도 / 롤백 스위치 / 상담원 이관 항상 가능
7. 투자     구축비 + 월 운영비, 손익분기 봉쇄율 33%
8. 다음     성공 시 인텐트 3개 확대 → 아웃바운드 검토
```

---

## 실습 과제

1. **골든셋 40건**을 만든다 (5개 축 각 8건)
2. 합성 발화 주입 러너를 만들고 CI에 붙인다
3. 안정성 장치 6개를 모두 구현하고 각각 강제로 발동시켜 본다
4. 동시 통화 부하 테스트를 돌려 무너지는 지점을 찾는다
5. 자기 시스템의 **실제 분당 원가**를 측정한다 (추정 아님)
6. 손익분기 봉쇄율을 계산한다
7. **파일럿 제안서 1페이저**를 쓴다

---

## 자가진단

- [ ] 프롬프트를 바꾸고 5분 안에 회귀 결과를 볼 수 있다
- [ ] 합성 발화를 실시간 속도로 재생해야 하는 이유를 안다
- [ ] 안정성 장치 6가지를 모두 구현해봤다
- [ ] 동시 통화 몇 개까지 SLA를 지키는지 숫자로 말할 수 있다
- [ ] 자기 시스템의 분당 원가를 실측했다
- [ ] 손익분기 봉쇄율을 계산할 수 있다
- [ ] 파일럿 범위를 좁히는 이유를 설명할 수 있다
- [ ] 롤백 경로를 설계에 포함시켰다

## 최종 점검 — 면접에서 나올 질문들

전 phase를 통과했다면 아래에 모두 답할 수 있어야 합니다.

1. barge-in을 어떻게 구현했나요? TTS 취소 시 이미 전송된 오디오 버퍼는요?
2. 발화 종료부터 첫 오디오까지 몇 ms인가요? 어느 구간을 어떻게 줄였나요?
3. Speech-to-Speech 대신 캐스케이드를 쓴다면 왜인가요?
4. 전화망 8kHz에서 STT 정확도가 떨어지는데 어떻게 대응하나요?
5. 에이전트가 CRM 쓰기에 실패했는데 통화는 진행 중입니다. 어떻게 처리하나요?
6. 봉쇄율 목표를 어떻게 잡고 파일럿을 설계하겠습니까?
7. 동시 통화 50개에서 무슨 일이 일어나나요?
8. 프롬프트를 바꿨을 때 품질이 나빠지지 않았다는 걸 어떻게 증명하나요?

각 질문에 **자기 프로젝트의 숫자로** 답할 수 있으면 준비가 끝난 것입니다.
