# 11. 도구를 쥔 모델

## 말만 하는 봇은 팔리지 않는다

"예약 현황을 알려드릴게요"까지만 하는 봇은 파일럿에서 죽습니다. 고객이 돈을 내는
건 "예약을 변경해 드렸습니다"입니다.

LLM은 텍스트를 생성할 뿐 아무것도 실행하지 못합니다. 실제로 일을 하려면 외부
시스템을 호출할 방법이 필요합니다. 그게 **도구 호출**(tool calling)입니다.

## 어떻게 동작하는가

기본 발상은 단순합니다. 모델에게 사용 가능한 함수 목록을 알려주고, "필요하면
호출하라"고 합니다.

```
1. 우리가 알려줌:   "lookupReservation(phone) 이런 함수가 있어"
2. 모델이 판단:     "사용자가 예약을 물어보네. 이 함수를 써야겠다"
3. 모델이 출력:     lookupReservation(phone="01012345678")
4. 우리가 실행:     실제 DB 조회
5. 결과를 돌려줌:   { date: "2026-08-03", time: "19:00", ... }
6. 모델이 답변 생성: "8월 3일 저녁 7시로 예약되어 있습니다"
```

**모델은 함수를 실행하지 않습니다.** "이 함수를 이 인자로 부르고 싶다"는 의사만
표현하고, 실제 실행은 우리 코드가 합니다. 이 구분이 중요합니다. 실행 권한이
우리에게 있으니 검증하고, 거부하고, 승인을 요구할 수 있습니다.

## 순진한 접근: 함수 이름만 잘 지으면 된다

```
lookupReservation(phone: string)
  "예약을 조회한다"
```

이렇게 정의하면 대충 동작합니다. 그리고 미묘하게 자주 실패합니다.

- 사용자가 예약을 언급했는데 호출하지 않고 그냥 대답을 지어냄
- 전화번호가 없는데 임의의 값을 넣어 호출
- 아무 맥락 없이 불필요하게 호출
- 다른 함수를 먼저 불러야 하는데 순서를 지키지 않음

## 왜 그런가: 설명문이 곧 프롬프트다

모델이 도구를 부를지 말지 결정할 때 보는 정보는 **함수 이름과 설명문**뿐입니다.
설명문이 곧 프롬프트입니다. 그런데 대부분의 개발자는 설명문을 문서 주석처럼 씁니다.

```
나쁨:  "예약을 조회한다"
       → 무엇을 하는지만 말함. 언제 부를지는 모델이 알아서 추측
```

```
좋음:  "전화번호로 기존 예약을 조회한다.
        사용자가 기존 예약을 언급하거나 변경·취소를 요청하면 반드시 먼저 호출할 것.
        전화번호를 모르면 먼저 사용자에게 물어볼 것."
       → 언제 부를지, 사전 조건이 무엇인지 명시
```

**"무엇을 하는가"가 아니라 "언제 부를 것인가"를 쓰는 것.** 이 하나로 도구 호출
정확도가 눈에 띄게 달라집니다. 스키마만으로는 순서나 사전 조건을 강제할 수
없기 때문에, 설명문이 그 역할을 대신합니다.

인자에도 같은 원칙이 적용됩니다.

```
나쁨:  date: string
좋음:  date: string  — "ISO 8601 형식, 타임존 포함. 예: 2026-08-03T19:00:00+09:00"
```

## 음성에서 특히 달라지는 것

도구 호출 자체는 챗봇과 같지만, 음성이라는 매체가 두 가지 제약을 추가합니다.

### 하나. 도구 호출은 침묵이다

DB를 조회하는 2초 동안 봇은 아무 말도 하지 않습니다. 채팅이라면 로딩 표시로
충분하지만 전화에서는 연결이 끊긴 것처럼 느껴집니다.

그래서 **도구 호출 전에 뭐라도 말해야 합니다.**

```
"네, 확인해 볼게요."   ← 미리 캐시된 음성, 지연 0
   (그동안 DB 조회)
"8월 3일 저녁 7시로 되어 있네요."
```

이 필러가 없으면 같은 2초가 훨씬 길게 느껴집니다. 9장에서 본 체감 지연 문제입니다.

### 둘. 호출 횟수가 지연에 직결된다

모델이 도구를 세 번 연달아 부르면 지연이 세 배입니다.

```
lookupCustomer → lookupReservation → checkAvailability
   400ms            300ms                600ms          = 1.3초
```

챗봇에서는 견딜 만하지만 통화 중에는 치명적입니다. 대응 방법이 몇 가지 있습니다.

- **한 번에 여러 개를 병렬 호출**하도록 유도 (독립적인 조회라면)
- **자주 쓰이는 조합을 하나의 도구로 합침** (`getCustomerContext`가 고객+예약을 한 번에)
- 최대 호출 횟수를 제한하고 초과 시 상담원 이관

세 번째가 중요합니다. 모델이 도구 호출 루프에 빠지면 통화비만 나가고 사용자는
계속 기다립니다. **반드시 상한을 둬야 합니다.**

## 구조화된 출력이라는 사촌

도구 호출과 형제 관계인 기능이 있습니다. 모델의 응답 자체를 정해진 스키마로
강제하는 것입니다.

```
통화 스크립트 → 모델 → { intent: "예약", date: "2026-08-03", partySize: 4 }
```

음성에서 이게 특히 중요한 이유는 **입력이 지저분하기 때문**입니다(2장). 구어체와
STT 오인식이 섞인 텍스트에서 구조화된 정보를 뽑아내야 하는데, 자유 텍스트로
받아서 파싱하면 실패율이 높습니다.

여기서 실무적인 함정이 하나 있습니다. 모델이 완벽한 JSON을 내놓지 않을 때가
있습니다. 코드펜스로 감싸거나, 후행 쉼표를 붙이거나, 마지막 따옴표를 빠뜨립니다.
일반 파서는 여기서 예외를 던지고, 통화 하나가 통째로 실패합니다.

그래서 **스키마에 맞춰 복구를 시도하는 파서**를 쓰는 접근이 있습니다. 깨진 JSON을
버리는 대신 스키마 정보를 이용해 고쳐 읽는 방식입니다. 통화당 실패 한 번이
곧 매출 손실인 환경에서는 이 차이가 작지 않습니다.

## 어떤 도구를 만들 것인가

도구를 잘게 쪼갤지 크게 묶을지도 설계 판단입니다.

| | 잘게 쪼갬 | 크게 묶음 |
|---|---|---|
| 유연성 | 높음 | 낮음 |
| 호출 횟수 | 많음 → 느림 | 적음 → 빠름 |
| 모델의 실수 여지 | 많음 (순서, 조합) | 적음 |
| 재사용성 | 높음 | 낮음 |

음성에서는 **큰 쪽으로 기우는 편이 낫습니다.** 지연이 비싸고, 모델이 순서를
틀릴 여지를 줄이는 게 안전하기 때문입니다. 챗봇이라면 잘게 쪼개서 유연하게
쓰는 게 좋지만, 통화 중에는 예측 가능성이 더 값집니다.

## 남는 질문

지금까지는 도구가 **읽기**라고 가정했습니다. 조회는 실패해도 다시 하면 됩니다.

그런데 **쓰기**는 다릅니다. 예약을 만들고, 결제를 하고, 취소를 합니다. 실패하면
되돌릴 수 없고, 두 번 실행되면 사고입니다. 그리고 그 와중에 사용자는 전화를 들고
기다리고 있습니다.

여기서부터 난이도가 한 단계 올라갑니다. 다음 장의 주제입니다.

**한 문장 요약**
도구의 설명문은 문서가 아니라 프롬프트이며, "무엇을 하는가"가 아니라 "언제 부를
것인가"를 써야 하고, 음성에서는 호출 하나하나가 지연이자 침묵이다.
