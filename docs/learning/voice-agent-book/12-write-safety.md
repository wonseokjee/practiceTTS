# 12. 통화는 되돌릴 수 없다

## 사용자는 지금 기다리고 있다

채팅에서 API가 실패하면 에러 메시지를 띄우고 사용자가 다시 시도합니다. 아무
문제 없습니다.

통화 중에는 그럴 수 없습니다. 사용자는 수화기를 들고 **지금** 기다리고 있고,
봇은 뭐라도 말해야 하며, 이미 "예약해 드릴게요"라고 말해버렸을 수도 있습니다.

이 장은 쓰기 작업의 안전장치를 다룹니다. 읽기는 누구나 하지만, 쓰기를 안전하게
하는 건 설계가 필요합니다.

## 문제 하나: 같은 요청이 두 번 간다

### 어떻게 벌어지는가

```
봇: createReservation(...) 호출
    → 네트워크 타임아웃
    → 재시도
    → 성공
결과: 예약 2건 생성
```

첫 요청이 실제로는 성공했는데 응답만 못 받은 경우입니다. 재시도하면 중복입니다.

통화 환경에서는 이게 특히 자주 일어납니다. 통화가 끊겼다 재연결되거나, 사용자가
같은 요청을 반복하거나, 시스템이 자동 재시도를 하거나.

### 그래서: 멱등성 키

요청마다 고유한 키를 붙이고, 같은 키가 이미 처리됐으면 **다시 실행하지 않고
이전 결과를 돌려줍니다.**

```
요청 1: key="CA123:create:7"  → 실행하고 결과 저장
요청 2: key="CA123:create:7"  → 이미 있음. 저장된 결과 반환 (실행 안 함)
```

키를 어떻게 만드느냐가 관건입니다. `통화ID + 도구이름 + 턴번호` 조합이 흔한
패턴인데, 이렇게 하면 같은 턴의 재시도는 같은 키를 갖고, 사용자가 진짜로 두 번
예약하면 턴이 다르므로 다른 키를 갖습니다.

## 문제 둘: 성공했는지 실패했는지 모른다

실패에는 종류가 있고, **가장 위험한 건 타임아웃**입니다.

| 실패 유형 | 상태 | 대응 |
|---|---|---|
| 400 검증 오류 | 확실히 실패 | 봇이 스스로 고쳐서 재시도 가능 |
| 500 서버 오류 | 확실히 실패 | 재시도하거나 이관 |
| **타임아웃** | **모름** | **가장 위험** |

타임아웃은 요청이 도달했는지, 처리됐는지, 응답만 유실됐는지 알 수 없습니다.

- 재시도하면 → 중복 처리 위험
- 포기하면 → 미처리 위험

**멱등성 키가 있으면 안전하게 재시도할 수 있습니다.** 이미 처리됐으면 중복되지
않고, 안 됐으면 이번에 처리됩니다. 앞의 두 문제가 여기서 연결됩니다.

멱등성이 없다면 선택지는 하나뿐입니다. 상태를 조회해서 확인하는 것.

```
타임아웃 → "예약이 생성됐는지" 조회 → 없으면 재시도, 있으면 성공 처리
```

조회 한 번이 더 들지만 중복보다는 낫습니다.

## 문제 셋: 실패했는데 통화가 진행 중이다

기술적 처리가 끝나도 **사용자에게 뭐라고 말할지**가 남습니다.

여기서 원칙 하나. **봇이 해결할 수 없는 상황이면 빨리 사람에게 넘깁니다.**

```
나쁨:  "죄송합니다, 다시 시도해 보겠습니다."
       (또 실패) "죄송합니다, 다시 시도해 보겠습니다."
       → 사용자는 같은 말을 세 번 듣고 끊음

좋음:  "지금 시스템 확인이 어려워서, 상담원에게 연결해 드릴게요.
        말씀해 주신 내용은 전달해 두겠습니다."
       → 한 번에 이관, 수집한 정보도 함께 전달
```

재시도는 한 번이면 충분합니다. 두 번 실패하면 봇이 해결할 문제가 아닙니다.

그리고 이관할 때 **지금까지 수집한 정보를 함께 넘기는 것**이 핵심입니다. 이게
없으면 사용자는 상담원에게 처음부터 다시 설명해야 하고, 그러면 봇을 거친 게
순수한 낭비가 됩니다. 14장에서 다룰 warm transfer가 이것입니다.

## 문제 넷: 위험한 일을 봇이 마음대로 한다

취소, 환불, 금액 변경 같은 액션은 잘못되면 돌이키기 어렵습니다.

여기서 **사람 승인 게이트**를 둡니다.

```
봇: "예약을 취소하시는 게 맞을까요? 취소 수수료 1만원이 발생합니다."
사용자: "네"
    → 작업을 일시 정지, 슈퍼바이저에게 승인 요청
    → 승인되면 실행
```

어디까지 자동화하고 어디부터 승인을 받을지는 **비즈니스 결정이지 기술 결정이
아닙니다.** 고객사마다 위험 감수 성향이 다릅니다. 그래서 설정으로 빼두고 고객이
정하게 하는 게 맞습니다.

판단 기준으로 쓸 만한 것: **되돌릴 수 있는가, 그리고 틀렸을 때 얼마나 비싼가.**

| 액션 | 되돌리기 | 승인 필요? |
|---|---|---|
| 예약 조회 | — | 불필요 |
| 예약 생성 | 쉬움 | 불필요 |
| 예약 변경 | 쉬움 | 대개 불필요 |
| 예약 취소 (수수료 발생) | 어려움 | 필요 |
| 환불 처리 | 어려움 | 필요 |

## 문제 다섯: 무슨 일이 있었는지 설명할 수 없다

"AI가 왜 이 예약을 바꿨나요?"

이 질문에 답하지 못하면 엔터프라이즈에 들어갈 수 없습니다. 감사 로그가 필요합니다.

남겨야 하는 것들:

- 어떤 통화의 몇 번째 턴인가
- 어떤 도구를 어떤 인자로 호출했는가
- 그때 사용자가 뭐라고 말했는가 (해당 구간 전사)
- 승인이 있었다면 누가 승인했는가
- 결과는 무엇이었는가
- 멱등성 키는 무엇이었는가

마지막 항목이 실무에서 의외로 요긴합니다. 중복 의심 건이 생겼을 때 같은 키인지
확인하면 바로 판정됩니다.

## 개인정보를 흘리지 않기

통화 전사에는 온갖 것이 들어옵니다. 주민번호, 카드번호, 계좌번호.

정규식으로 패턴을 잡아 마스킹하는 게 1차 방어선입니다. 다만 한계가 분명합니다.

- 사용자가 띄어 읽으면 패턴이 안 맞음 ("육이공일공일 다시, 일이삼사")
- STT 오인식으로 숫자가 틀리면 패턴을 빗나감
- 문맥 없이는 그냥 숫자인지 주민번호인지 구분 못 함

그리고 **한글 텍스트에서 정규식 단어 경계는 제대로 동작하지 않습니다.** 한글은
정규식이 가정하는 "단어 문자" 집합에 포함되지 않아서 경계 판정이 어긋납니다.
영어 기준으로 짠 마스킹 패턴을 그대로 가져오면 한글 앞뒤에서 조용히 실패합니다.

완전한 차단에는 문맥을 보는 개체명 인식(NER)이 필요합니다. 정규식은 1차
방어선이지 최종 답이 아니라고 봐야 합니다.

## 남는 질문

지금까지의 장치들은 전부 **실패를 전제한 설계**입니다. 실패는 반드시 일어나고,
그때 무엇을 할지 미리 정해두는 것.

그런데 진짜 어려운 건 실패를 **알아채는 것**입니다. API가 200을 반환했지만
실제로는 엉뚱한 예약이 만들어졌다면? 봇이 사용자 말을 오해해서 잘못된 날짜로
정확하게 처리했다면?

이런 실패는 로그에 에러로 남지 않습니다. 모든 게 정상으로 보입니다. 그래서
다음 장이 필요합니다.

---

**한 문장 요약**
쓰기 작업의 안전은 멱등성 키, 재시도 상한, 빠른 이관, 승인 게이트, 감사 로그로
만들어지고, 그중 타임아웃 처리가 가장 위험하며 멱등성이 그 열쇠다.

**스스로 답해보기**

2. 멱등성 키를 통화ID + 도구명 + 턴번호로 만드는 이유는?
3. 어떤 액션에 사람 승인을 붙일지 판단하는 기준 두 가지는?
