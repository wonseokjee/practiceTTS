# 03. 마이크에서 스피커까지

## 소리가 숫자가 되는 과정

이 장은 나머지 전부의 밑바탕입니다. 여기서 나오는 세 개의 숫자 — 샘플레이트,
비트 깊이, 프레임 크기 — 가 4장부터 계속 되돌아옵니다.

소리는 공기의 압력 변화입니다. 연속적인 파동이죠. 컴퓨터는 연속적인 것을 다룰 수
없으니 **일정 간격으로 값을 찍어서** 숫자 배열로 만듭니다. 이걸 샘플링이라고 합니다.

```
실제 소리 (연속)     ∿∿∿∿∿∿∿∿∿∿∿
샘플링 (이산)        · · · · · · · · · ·
저장된 값            [0, 12, 30, 25, -8, -40, ...]
```

## 샘플레이트 — 1초에 몇 번 찍는가

초당 찍는 횟수가 샘플레이트입니다. 단위는 Hz.

| 샘플레이트 | 쓰이는 곳 |
|---|---|
| 8,000 Hz | **전화망** |
| 16,000 Hz | 음성 인식 모델의 표준 입력 |
| 24,000 Hz | 최근 TTS 모델의 출력 |
| 44,100 Hz | CD 음질 |
| 48,000 Hz | WebRTC 기본, 영상 제작 |

여기서 결정적인 규칙이 하나 있습니다. **나이퀴스트 정리**입니다.

> 샘플레이트의 절반보다 높은 주파수는 기록할 수 없다.

8,000Hz로 샘플링하면 4,000Hz 이상의 소리는 아예 사라집니다. 조금 뭉개지는 게
아니라 **없어집니다.** 나중에 아무리 업샘플링해도 복원되지 않습니다. 없는 정보를
만들어낼 수는 없으니까요.

사람 목소리의 기본 주파수는 100~300Hz 정도지만, 자음을 구분하는 정보는 훨씬 높은
대역에 있습니다. ㅅ, ㅆ, ㅎ 같은 마찰음은 4,000Hz 이상에 에너지가 몰려 있습니다.
8kHz 전화에서 이 소리들이 서로 구분되지 않는 이유입니다. 4장에서 자세히 다룹니다.

## 비트 깊이 — 한 번에 얼마나 정밀하게

찍은 값을 몇 비트로 저장하느냐입니다. 16비트면 65,536단계로 진폭을 표현합니다.
음성에서는 16비트가 사실상 표준이고, 이 숫자 때문에 고민할 일은 거의 없습니다.

다만 전화망은 여기서도 특이합니다. 8비트만 쓰면서 **µ-law**라는 비선형 압축을
적용합니다. 작은 소리는 촘촘하게, 큰 소리는 성기게 기록하는 방식인데, 사람 귀가
작은 소리 변화에 민감하다는 성질을 이용한 것입니다. 결과적으로 8비트로 13비트에
가까운 체감 품질을 냅니다. 1970년대에 만들어진 영리한 절충입니다.

## 프레임 — 소리를 다루는 단위

오디오를 한 샘플씩 처리하지는 않습니다. 일정 시간 묶음으로 다루는데, 이 묶음을
프레임이라고 합니다.

음성 통신에서는 **20밀리초**가 사실상 표준입니다. 왜 20ms인가. 더 짧게 자르면
패킷 헤더 오버헤드가 커지고, 더 길게 자르면 지연이 늘어납니다. 그 사이의 관행적
타협점입니다.

8kHz µ-law에서 20ms 프레임의 크기를 계산해보면 이렇습니다.

```
8,000 샘플/초 × 0.02초 = 160 샘플
µ-law는 샘플당 1바이트 → 160바이트
```

**160바이트.** 전화 오디오를 다루다 보면 이 숫자를 계속 보게 됩니다. Twilio Media
Streams 같은 서비스에서 오는 오디오 청크가 정확히 이 크기입니다. 이 숫자가 어디서
왔는지 알면 문서를 읽을 때 훨씬 편합니다.

## 코덱 — 압축해서 보내기

원본 그대로 보내면 대역폭이 큽니다. 그래서 압축합니다.

| 코덱 | 어디서 | 특징 |
|---|---|---|
| **G.711 (µ-law/A-law)** | 전화망 | 압축률 낮음, 지연 거의 0, 40년 넘게 현역 |
| **Opus** | WebRTC | 대역폭 적응, 8~48kHz 가변, 손실 은닉 우수 |
| **G.729** | 대역폭 절약형 VoIP | 압축률 높지만 음질 희생 |

G.711이 여전히 쓰이는 이유는 **호환성**입니다. 전 세계 어느 전화 장비든 이건
반드시 지원합니다. 그리고 압축이 거의 없어서 인코딩 지연이 없습니다. 대역폭이
싸진 시대에 압축률은 더 이상 중요한 문제가 아닙니다.

## 샘플레이트 변환이라는 잔업

파이프라인을 조립하다 보면 각 구성요소가 요구하는 샘플레이트가 다릅니다.

```
전화망 8kHz  →  STT 모델 16kHz  →  LLM(텍스트)  →  TTS 24kHz  →  전화망 8kHz
      ↑ 업샘플링                                          ↑ 다운샘플링
```

이 변환은 그냥 지나가는 잡일처럼 보이지만 두 가지 함정이 있습니다.

첫째, **업샘플링은 정보를 복원하지 않습니다.** 8kHz를 16kHz로 올려도 사라진
고주파는 돌아오지 않습니다. STT 모델이 16kHz 입력을 받는다고 정확도가 회복되는
게 아닙니다. 형식만 맞춰줄 뿐입니다.

둘째, **변환에도 시간이 듭니다.** 품질 좋은 리샘플러는 필터를 쓰기 때문에 몇
밀리초의 지연을 추가합니다. 9장의 지연 예산에서 "네트워크·버퍼링" 항목에 조용히
포함되는 비용입니다.

## 남는 질문

여기까지가 "소리를 숫자로 다루는 법"의 최소한입니다. 그런데 왜 전화망만 유독
8kHz에 8비트라는 낡은 규격을 고수하고 있을까요. 바꾸면 되는 것 아닌가.

바꿀 수 없는 이유가 있습니다. 다음 장의 주제입니다.

---

사람 목소리에서 자음을 구분하는 대역을 통째로 잘라낸다.

**스스로 답해보기**
