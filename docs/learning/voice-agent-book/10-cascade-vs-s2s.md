# 10. 두 개의 아키텍처

## 소리를 텍스트로 바꿔야 하는가

지금까지 암묵적으로 하나의 구조를 전제했습니다.

```
음성 → [STT] → 텍스트 → [LLM] → 텍스트 → [TTS] → 음성
```

**캐스케이드**(cascade) 방식입니다. 세 개의 독립된 모델을 이어 붙인 것이죠.

그런데 왜 텍스트를 거쳐야 할까요. 소리를 받아 소리를 내놓는 모델 하나면 안 될까요.

```
음성 → [ 하나의 모델 ] → 음성
```

**Speech-to-speech**(S2S)입니다. OpenAI Realtime API와 Gemini Live API가
대표적입니다. 둘 중 무엇을 고를지가 이 장의 주제입니다.

## 캐스케이드의 비용

세 단계를 거치는 데서 오는 손해가 명확합니다.

**첫째, 지연이 누적됩니다.** 9장에서 본 대로입니다. 각 모델이 자기 몫의 시간을
쓰고, 그게 그대로 더해집니다.

**둘째, 정보가 버려집니다.** 이게 더 근본적인 문제입니다.

```
사용자가 실제로 말한 것:  "네... (한숨) 뭐 그렇게 해주세요."
                          └─ 짜증, 체념, 마지못함이 목소리에 담김

STT가 넘기는 것:          "네 뭐 그렇게 해주세요"
                          └─ 감정 정보 전부 소실
```

STT는 **단어만** 뽑아냅니다. 억양, 속도, 망설임, 한숨, 목소리 떨림 — 대화의
절반쯤을 차지하는 정보가 텍스트 변환 시점에 사라집니다. LLM은 그 사람이 화가
났는지 급한지 알 수 없습니다.

같은 일이 출력에서도 벌어집니다. LLM이 "죄송합니다"라는 텍스트를 내놓으면 TTS는
그걸 평범하게 읽습니다. 진심으로 미안한 톤인지, 형식적인 사과인지 구별할 정보가
없습니다.

## S2S가 푸는 것

하나의 모델이 소리를 직접 받고 직접 내놓으면 이 손실이 없습니다.

- 사용자의 감정과 어조를 그대로 인지
- 응답의 억양과 속도를 상황에 맞게 조절
- 중간 변환이 없으니 지연이 짧음
- 웃음, 한숨, 망설임 같은 비언어적 요소 표현 가능

실제로 써보면 차이가 확연합니다. 캐스케이드가 "잘 만든 자동응답"이라면, S2S는
"사람과 통화하는" 느낌에 훨씬 가깝습니다.

## 그런데 왜 아직 캐스케이드가 주류인가

특히 엔터프라이즈 컨택센터에서는 압도적으로 캐스케이드입니다. 이유가 있습니다.

### 감사와 컴플라이언스

금융, 의료, 보험 같은 규제 산업에서는 **모든 통화의 텍스트 기록**이 요구됩니다.
분쟁이 생겼을 때 "AI가 뭐라고 말했는가"를 증명할 수 있어야 합니다.

캐스케이드는 구조상 모든 턴의 텍스트가 남습니다. S2S는 별도로 전사해야 하고,
그 전사가 실제 발화와 정확히 일치한다는 보장이 약합니다.

### 결정성

법적으로 특정 문구를 반드시 말해야 하는 경우가 있습니다. 녹취 고지, 약관 안내,
AI 사용 고지 같은 것들이죠.

캐스케이드에서는 미리 만들어둔 오디오를 그 자리에 재생하면 끝입니다. S2S에서는
모델에게 "이 문장을 정확히 말해"라고 지시해야 하는데, 생성 모델은 본질적으로
확률적입니다. 매번 똑같이 말한다는 보장이 없습니다.

### 제어와 개입

캐스케이드는 각 단계 사이에 손을 넣을 수 있습니다.

```
STT 결과 → [PII 마스킹] → LLM
LLM 출력 → [금칙어 필터] → [문장 분할] → TTS
```

주민번호를 마스킹하고, 부적절한 표현을 거르고, 문장 단위로 잘라 보내는 처리를
중간에 끼워 넣습니다. S2S는 통째로 하나라 이런 개입 지점이 거의 없습니다.

### 비용과 벤더 선택

캐스케이드는 구간마다 최적의 조합을 고를 수 있습니다. STT는 A사, LLM은 B사,
TTS는 C사. 한 곳이 장애가 나면 그 구간만 다른 벤더로 바꿉니다.

S2S는 한 벤더에 통째로 종속됩니다. 그 모델이 느려지면 대안이 없습니다. 그리고
오디오 토큰은 텍스트 토큰보다 비쌉니다.

### 목소리 교체

고객사마다 다른 목소리를 원할 수 있습니다. 캐스케이드는 TTS만 바꾸면 됩니다.
S2S는 모델이 제공하는 목소리 중에서만 고를 수 있습니다.

## 나란히 놓고 보면

| | 캐스케이드 | Speech-to-Speech |
|---|---|---|
| 지연 | 누적됨 | 짧음 |
| 감정·억양 인지 | 불가 | 가능 |
| 감정·억양 표현 | 약함 | 강함 |
| 텍스트 감사 로그 | 자동 완비 | 별도 전사 필요 |
| 중간 개입 | 자유로움 | 거의 불가 |
| 특정 문구 보장 | 쉬움 | 어려움 |
| 목소리 교체 | TTS만 바꾸면 됨 | 모델에 종속 |
| 벤더 다변화 | 구간별 선택 | 통째로 종속 |
| 비용 | 조합 최적화 가능 | 오디오 토큰이 비쌈 |
| 도구 호출 | 자유로움 | 지원하나 제약 있음 |

## 그래서 어떻게 고르는가

정답은 요건이 정합니다. 판단 기준을 몇 개 두면 이렇습니다.

**S2S가 유리한 경우**
- 감정 인지가 제품 가치의 핵심 (상담, 코칭, 동반자형 서비스)
- 지연이 절대적으로 중요
- 규제가 약하고 감사 요구가 낮음
- 목소리와 페르소나가 고정되어도 됨

**캐스케이드가 유리한 경우**
- 규제 산업, 감사 로그 필수
- 반드시 말해야 하는 문구가 있음
- 도구 호출과 시스템 연동이 많음
- 여러 고객사에 다른 목소리로 납품
- 비용 통제가 중요

면접에서 이 주제가 나오면 **"S2S가 최신이니까 좋다"고 답하면 안 됩니다.**
위 표를 근거로 "이 요건에서는 이쪽"이라고 말할 수 있어야 합니다. 그게 기술을
아는 것과 제품을 아는 것의 차이입니다.

## 하이브리드라는 선택지

둘 중 하나를 고를 필요가 없을 수도 있습니다.

```
사용자 음성 ─┬─▶ S2S 모델 ──▶ 응답 음성
             └─▶ STT ──▶ 텍스트 기록 (감사용, 병렬)
```

S2S로 대화하면서 같은 오디오를 STT에도 흘려 텍스트 기록을 남기는 방식입니다.
비용은 더 들지만 감사 요구를 충족하면서 S2S의 자연스러움을 얻습니다.

또는 구간을 나눠서, 일반 대화는 S2S로 하고 결제나 예약 확정처럼 결정성이 필요한
구간만 캐스케이드로 전환하는 방식도 가능합니다. 복잡하지만 실제로 쓰이는 패턴입니다.

## 남는 질문

S2S의 약점 대부분은 **모델 내부를 들여다볼 수 없다**는 데서 옵니다. 감사도,
개입도, 결정성도 결국 같은 문제의 다른 얼굴입니다.

이건 시간이 해결할 문제일 수도 있습니다. S2S 모델이 자기 발화의 정확한 전사를
함께 내놓고, 중간에 제약을 걸 수 있는 인터페이스를 제공한다면 캐스케이드를 고를
이유가 크게 줄어듭니다.

지금 시점의 답은 **"S2S를 배우되 캐스케이드로 만들 줄 알아야 한다"**입니다.
엔터프라이즈 시장이 움직이는 속도는 모델이 발전하는 속도보다 훨씬 느립니다.

**한 문장 요약**
S2S는 감정과 지연에서 우월하지만 감사·결정성·개입·벤더 다변화에서 약하고,
규제 산업이 여전히 캐스케이드를 쓰는 이유는 전부 여기에 있다.
