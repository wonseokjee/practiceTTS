# 09. 800밀리초 예산

## 예산이라는 사고방식

1장에서 사람은 200밀리초에 대답한다고 했습니다. 기계가 거기에 도달하는 건 당분간
불가능합니다. 그러면 목표를 어디에 둬야 할까요.

경험적으로 **800밀리초**가 경계선입니다. 이 아래면 대화처럼 느껴지고, 1초를
넘어가면 "기다리는" 느낌이 시작되며, 1.5초를 넘으면 사용자가 말을 겹쳐 시작합니다.

여기서 중요한 건 숫자 자체가 아니라 **예산이라는 사고방식**입니다.

> 총 800ms를 각 구간에 배분한다. 한 구간이 초과하면 다른 구간에서 아껴야 한다.

이렇게 생각하기 시작하면 "느리다"는 막연한 불평이 "TTS TTFB가 예산 150ms인데
340ms 쓰고 있다"는 구체적 문제로 바뀝니다. 고칠 수 있는 형태가 됩니다.

## 예산 나누기

발화 종료부터 첫 오디오 출력까지를 다섯 구간으로 쪼갭니다.

| 구간 | 예산 | 무슨 일이 일어나는가 |
|---|---:|---|
| 종단 감지 | 200~300ms | 7장. "말이 끝났다"고 판정하기까지 |
| STT 확정 | 100ms | 부분 인식을 흘려보냈다면 대부분 상쇄됨 |
| LLM 첫 토큰 | 300~400ms | 프롬프트 길이와 모델 크기에 비례 |
| TTS 첫 바이트 | 100~150ms | 전체가 아니라 **첫 문장만** 나오면 됨 |
| 네트워크·버퍼 | 100ms | 6장. 지터 버퍼가 대부분 |
| **합계** | **800~1050ms** | |

**이 표를 외우는 게 목적이 아닙니다.** 자기 시스템에서 실제로 재서 자기 표를
만드는 것이 목적입니다. 남의 숫자는 참고값일 뿐이고, 구성이 다르면 배분도 달라집니다.

## 어디에 시간이 가는지 먼저 재라

가장 흔한 실수는 **재보지 않고 최적화하는 것**입니다.

"LLM이 느린 것 같다"고 짐작하고 더 작은 모델로 바꿨는데 총 지연이 그대로인
경우가 흔합니다. 실제 병목이 TTS였거나, 종단 감지에서 500ms를 쓰고 있었거나.

구간별로 시간을 찍어서 기록해야 합니다. 그리고 **평균이 아니라 p95를 봐야**
합니다. 이게 음성에서 특히 중요합니다.

```
p50 (중앙값)  720ms   ← "괜찮은데?"
p95           1,850ms ← 스무 번에 한 번 이렇게 됨
```

통화 한 건에 턴이 열 번이면, p95가 나쁜 시스템은 **거의 모든 통화에서 최소 한 번**
어색한 침묵이 발생합니다. 사용자는 평균을 기억하지 않습니다. 이상했던 순간을
기억합니다.

## 예산을 지키는 세 가지 방법

### 하나. 겹친다

1장의 결론입니다. 각 단계를 빠르게 만드는 것보다 겹치는 것이 이득이 큽니다.

**부분 인식으로 미리 시작**하는 것이 대표적입니다. STT의 최종 확정을 기다리지 않고,
부분 결과가 안정되면 LLM 요청을 투기적으로 보냅니다. 예측이 맞으면 300~400ms를
통째로 아낍니다. 틀리면 버리고 다시 하는데, 그 비용이 아끼는 시간보다 쌉니다.

### 둘. 첫 문장만 먼저 보낸다

LLM이 답변을 다 만들 때까지 기다릴 이유가 없습니다. 첫 문장이 완성되는 순간
TTS로 넘겨 재생을 시작하고, 나머지는 재생되는 동안 생성합니다.

```
기다렸다 한 번에:  [────── LLM 전체 ──────][── TTS ──]♪   총 1,800ms
문장 단위로 흘림:  [─ 첫 문장 ─][TTS]♪                     총 600ms
                              [─ 둘째 ─][TTS]♪  ← 재생 중에 생성
```

**답변이 길수록 이득이 커집니다.** 세 문장짜리 답변에서 첫 문장만 먼저 보내면
체감 지연이 3분의 1로 줍니다.

문장 경계를 찾는 게 관건인데, 한국어는 종결어미가 명확해서 상대적으로 쉽습니다.
다만 너무 짧게 자르면 TTS 호출이 잦아져 오버헤드가 늘고, 문장 사이 억양이
부자연스러워집니다.

### 셋. 침묵을 메운다

이건 실제 지연을 줄이지 않습니다. **체감 지연만 줄입니다.** 그런데 효과가 큽니다.

도구를 호출하느라 2초가 걸리는 구간이 있다고 합시다. 그냥 침묵하면 사용자는
연결이 끊긴 줄 압니다. 여기에 "네, 확인해 볼게요"를 재생하면 같은 2초가
"일하고 있구나"로 바뀝니다.

이 문구들은 매번 생성할 필요가 없습니다. 고정된 문장이므로 **미리 만들어 캐시해두면**
지연 0에 비용 0으로 재생됩니다. 사전 생성 TTS 캐시를 갖춰두는 것이 여기서
그대로 값어치를 합니다.

## 예산을 지키기 위해 포기하는 것들

지연은 다른 모든 것과 경쟁합니다.

| 아끼는 방법 | 대신 잃는 것 |
|---|---|
| 종단 감지 임계값을 줄임 | 사용자 말을 끊을 확률 증가 |
| 더 작은 LLM 사용 | 답변 품질, 도구 호출 정확도 |
| 프롬프트를 짧게 | 행동 제어력 |
| 지터 버퍼 축소 | 음질, 끊김 |
| 투기적 실행 | 버려지는 토큰 비용 |
| 대화 이력 잘라내기 | 맥락 유지 |

**공짜로 얻는 건 "겹치기"뿐입니다.** 그래서 겹칠 수 있는 것부터 전부 겹치고,
그 다음에 무엇을 희생할지 고르는 순서가 맞습니다.

## 전화는 예산이 더 빡빡하다

브라우저에서 800ms를 맞췄다고 전화에서도 맞는 게 아닙니다.

```
브라우저:  마이크 → WebRTC → 서버
전화:      마이크 → 캐리어망 → SIP trunk → 게이트웨이 → 서버
                    └── 여기서 100~200ms 추가 ──┘
```

전화망을 거치는 것만으로 100~200ms가 더해집니다. 브라우저에서 850ms였던 것이
전화에서 1,050ms가 됩니다. 그리고 8kHz 열화로 STT가 더 자주 틀려서 되묻는 턴이
늘어납니다. 되묻는 턴 하나가 통째로 추가 지연입니다.

**전화용 예산은 브라우저보다 더 공격적으로 잡아야 합니다.**

## 남는 질문

800ms는 어디까지나 관행적 목표입니다. 그런데 정말 모든 상황에서 800ms가
필요할까요.

사용자가 복잡한 질문을 했다면 잠깐 뜸을 들이는 게 오히려 자연스럽습니다.
사람도 어려운 질문에는 "음..." 하고 생각합니다. 즉답이 항상 좋은 건 아닙니다.

반대로 "네" 같은 간단한 확인에는 200ms도 길게 느껴집니다.

**질문의 성격에 따라 예산을 다르게 잡는 것**이 다음 단계인데, 아직 이렇게 하는
시스템은 드뭅니다. 그리고 "이 질문이 어려운가"를 판단하는 것 자체가 또 시간이
드는 일이라는 순환 문제가 있습니다.

---

**한 문장 요약**
지연은 총량을 구간에 배분하는 예산 문제이고, 겹치기만이 공짜이며, 나머지는
전부 무언가를 희생해서 얻는다.

3. 지연을 줄이기 위해 희생할 수 있는 것들을 세 가지 들고, 각각 무엇을 잃는지 말해보라.
