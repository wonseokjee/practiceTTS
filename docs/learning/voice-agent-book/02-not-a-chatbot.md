# 02. 텍스트 챗봇과 무엇이 다른가

## 같은 LLM, 완전히 다른 제품

음성 에이전트의 "두뇌"는 텍스트 챗봇과 같은 LLM입니다. 그래서 챗봇을 만들어본
사람은 "음성 입출력만 붙이면 되겠네"라고 생각합니다. 그리고 대부분 실패합니다.

매체가 바뀌면 제품이 바뀝니다. 무엇이 달라지는지 다섯 가지로 나눠 봅니다.

## 하나. 되돌릴 수 없다

채팅에서는 메시지를 보내고 나서 수정할 수 있습니다. 스트리밍 중에 이상한 답이
나오면 중단 버튼을 누르고 다시 시킬 수 있습니다. 사용자는 화면을 위로 스크롤해
앞의 대화를 다시 읽을 수 있습니다.

음성은 전부 불가능합니다. 한 번 스피커로 나간 소리는 회수되지 않습니다. 사용자는
방금 들은 문장을 다시 들을 수 없습니다. 봇이 잘못된 예약 날짜를 말해버리면
"아까 말씀드린 건 취소하고"로 수습해야 하는데, 사용자 머릿속에는 이미 틀린 날짜가
들어가 있습니다.

이 성질이 설계에 직접 영향을 줍니다. **확정적인 발화는 확정된 뒤에 해야 합니다.**
"예약해 드렸습니다"를 API 호출 전에 말하면 안 됩니다. 채팅이라면 실패 메시지를
뒤에 덧붙이면 되지만, 음성에서는 이미 늦었습니다.

## 둘. 기다려주지 않는다

채팅에서 3초는 아무것도 아닙니다. 사용자는 다른 탭을 보다가 돌아옵니다. 로딩
스피너가 돌고 있으면 "생각 중이구나" 하고 기다립니다.

전화에서 3초 침묵은 사고입니다. 시각적 단서가 전혀 없기 때문에 사용자는 침묵을
"연결이 끊겼다"로 해석합니다. 여보세요를 두 번 하고 끊습니다.

그래서 음성 에이전트에는 채팅에 없는 장치가 필요합니다. 도구를 호출하느라 시간이
걸리는 구간에 "네, 확인해 볼게요" 같은 **필러 음성**을 재생하는 것이 대표적입니다.
내용상 아무 의미 없는 문장이지만, 침묵을 메우는 것만으로 체감 지연이 크게 줄어듭니다.

## 셋. 입력이 지저분하다

채팅 입력은 사용자가 쓰고 읽어보고 보낸 문장입니다. 음성 입력은 그렇지 않습니다.

```
채팅:  "다음 주 수요일 저녁 7시에 4명 예약하고 싶어요"

음성:  "어 그 다음주에 화요일 아니 수요일인가 저녁에 한 일곱시쯤
        네 명이요 아 근데 주차 되나요"
```

말은 계획 없이 나옵니다. 중간에 정정하고, 되짚고, 딴 얘기로 샙니다. 여기에 STT
오인식까지 얹힙니다. "네 명"이 "내 명"으로, "화요일"이 "화용일"로 들어옵니다.

그래서 음성 에이전트의 프롬프트는 채팅과 다르게 써야 합니다. 정정을 예상하고,
확신이 없으면 되묻고, 부분 정보로도 진행할 수 있어야 합니다.

## 넷. 길게 말하면 안 된다

채팅에서 긴 답변은 오히려 친절합니다. 사용자가 필요한 부분만 눈으로 훑을 수
있으니까요.

음성에서 긴 답변은 고문입니다. 건너뛸 수 없고, 앞부분을 다시 볼 수 없고, 목록을
읽어주면 세 번째 항목쯤에서 첫 번째를 잊습니다. 전화로 "다음 다섯 가지 옵션이
있습니다"를 듣는 경험을 떠올려보면 됩니다.

음성 에이전트의 시스템 프롬프트에 거의 항상 들어가는 지시가 있습니다.

```
- 답변은 두 문장을 넘기지 않습니다.
- 한 번에 하나씩만 물어봅니다.
- 목록을 나열하지 않습니다. 가장 적절한 하나를 제안하고 다른 걸 원하는지 묻습니다.
```

같은 모델이라도 이 지시가 있고 없고의 차이가 제품의 성패를 가릅니다.

## 다섯. 사용자가 끼어든다

채팅에는 없는 개념입니다. 음성에서는 봇이 말하는 도중에 사용자가 말을 시작합니다.
자주, 그리고 정당하게. 봇이 엉뚱한 소리를 하기 시작하면 끝까지 듣고 있을 이유가
없습니다.

끼어들기를 처리하지 않는 봇은 사용자가 말을 걸어도 계속 떠듭니다. 이 순간
사용자는 "아, 이거 로봇이구나"라고 확신합니다. 대화가 아니라 자동응답기라는 걸
알아채는 지점입니다.

끼어들기는 8장에서 따로 다룹니다. 구현이 생각보다 훨씬 까다롭기 때문입니다.

## 정리하면

| | 텍스트 챗봇 | 음성 에이전트 |
|---|---|---|
| 출력 회수 | 가능 | 불가능 |
| 3초 침묵 | 괜찮음 | 사고 |
| 입력 품질 | 정제됨 | 지저분함 |
| 긴 답변 | 친절함 | 고문 |
| 끼어들기 | 없는 개념 | 핵심 기능 |
| 실패 시 | 다시 시도 | 통화가 진행 중 |

마지막 줄이 가장 중요합니다. 채팅에서 API가 실패하면 에러 메시지를 띄우고 사용자가
다시 시도하면 됩니다. 통화 중에는 그럴 수 없습니다. 사용자는 수화기를 들고
**지금 기다리고 있습니다.** 이 제약이 4부 전체의 배경입니다.

## 남는 질문

이 차이들은 대부분 "매체가 실시간이고 되돌릴 수 없다"에서 파생됩니다. 그런데
왜 실시간인가. 사용자가 녹음을 보내고 몇 초 뒤에 답을 받는 비동기 음성이라면
이 문제들이 거의 사라집니다.

실제로 그런 제품도 있습니다. 다만 사람들이 전화를 거는 이유는 대개 **지금 당장
해결하고 싶어서**입니다. 비동기로 만들면 매체가 주는 가치가 함께 사라집니다.
제약을 없애는 대신 안고 가는 쪽을 택하는 것입니다.

---

**한 문장 요약**
음성은 되돌릴 수 없고, 기다려주지 않고, 입력이 지저분하고, 길게 말할 수 없고,
사용자가 끼어드는 매체다. 같은 LLM을 써도 완전히 다른 제품이 된다.
