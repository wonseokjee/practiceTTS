# 16. 파일럿은 좁을수록 좋다

## 첫 도입이 어려운 이유

기술은 됩니다. 원가도 맞습니다. 그런데 고객사가 도입을 결정하지 않습니다.

이유는 대개 기술이 아닙니다. **고객사 담당자 입장에서 실패했을 때 자기가 책임을
져야 하기 때문**입니다. AI가 고객에게 이상한 소리를 하면 그건 그 사람의 실책이
됩니다. 그래서 아무리 좋아 보여도 첫 발을 떼기가 어렵습니다.

파일럿 설계의 목적은 **이 두려움을 줄이는 것**입니다. 성능을 자랑하는 게 아니라
"실패해도 안전하다"를 설계로 보여주는 일입니다.

## 순진한 접근

```
"저희 AI가 고객 문의 전반을 처리할 수 있습니다.
 6개월 도입하시면 상담 인력을 30% 줄일 수 있습니다."
```

전부 틀렸습니다.

- **범위가 너무 넓다** — "문의 전반"은 측정도 통제도 불가능
- **기간이 너무 길다** — 6개월 뒤에 실패하면 담당자가 책임짐
- **목표가 위협적이다** — "인력 30% 감축"은 내부 저항을 부름
- **성공 기준이 없다** — 무엇을 달성하면 성공인지 불명확

## 좁히기

파일럿의 첫 번째 원칙은 **범위를 아프도록 좁히는 것**입니다.

```
나쁨:  "고객 문의 전반"
좋음:  "예약 변경 인바운드 통화만" (전체 통화의 약 25%)
```

좁히면 세 가지가 좋아집니다.

**품질이 올라갑니다.** 11장에서 봤듯 도메인이 좁을수록 어휘 힌트가 잘 듣고,
프롬프트가 명확해지고, 골든셋을 촘촘하게 만들 수 있습니다.

**측정이 가능해집니다.** "예약 변경 통화 중 몇 %를 봇이 끝냈는가"는 셀 수 있지만,
"문의 전반이 개선되었는가"는 셀 수 없습니다.

**실패해도 작습니다.** 25%의 통화에서 문제가 생겨도 나머지 75%는 평소대로
돌아갑니다.

> 단일 인텐트에서 봉쇄율 80%를 내는 것이, 모든 인텐트에서 30%를 내는 것보다
> 훨씬 좋은 파일럿입니다. 확장은 그 다음입니다.

## 숫자로 된 성공 기준

시작 전에 합의해야 합니다. 끝나고 나서 정하면 아무도 만족하지 않습니다.

```
1차 목표:  대상 통화 봉쇄율 40% 이상
제약 조건: CSAT 도입 전 수준 유지 (4.2 → 4.0 이상)
부가 지표: 대상 통화 AHT 20% 감소
```

**제약 조건이 목표만큼 중요합니다.** 봉쇄율만 걸어두면 14장의 함정에 빠집니다.
CSAT 하한선을 함께 걸어야 정상적인 최적화가 일어납니다.

## 짧게, 그리고 비교군과 함께

```
1주차:  셋업, 내부 테스트
2~3주차: 실트래픽 50% 라우팅
4주차:  분석 및 판단
```

4주면 충분합니다. 길게 잡을수록 담당자의 위험이 커집니다.

**50% 라우팅**이 핵심입니다. 전량을 봇에게 보내면 비교 대상이 없어서 "좋아졌다"를
증명할 수 없습니다. 같은 기간의 나머지 50%가 대조군이 됩니다. 계절 효과나 특이
이벤트의 영향도 자동으로 상쇄됩니다.

## 롤백 스위치

기술적으로는 간단하지만 심리적으로 결정적입니다.

```
"이상하면 스위치 하나로 전량 상담원 라우팅으로 돌아갑니다. 즉시, 배포 없이."
```

이 한 문장이 도입 결정을 앞당깁니다. 담당자가 "최악의 경우"를 상상했을 때
빠져나갈 길이 보이기 때문입니다.

실제로 눌릴 일은 거의 없습니다. 그래도 있어야 합니다. **되돌릴 수 있다는 사실이
결정을 만듭니다.**

## 제안서 한 장

파일럿 제안은 한 페이지를 넘기지 않는 게 좋습니다. 구성은 대략 이렇습니다.

```
1. 현황     월 통화량, 현재 AHT, 포기율, 인력 규모
            → 고객사 숫자로 시작. 우리 기술 얘기 아님

2. 범위     "예약 변경 인바운드만" — 전체의 약 25%
            → 구체적으로, 그리고 좁게

3. 목표     봉쇄율 40% / CSAT 4.0 이상 유지 / AHT 20% 감소
            → 목표와 제약을 함께

4. 기간     4주 (1주 셋업 + 2주 운영 + 1주 분석)

5. 측정     A/B 50:50, 주간 리포트, 지표 정의 명시

6. 리스크   STT 정확도 한계 / 롤백 스위치 / 상담원 이관 항상 가능
            → 리스크를 먼저 말하는 쪽이 신뢰를 얻음

7. 투자     구축비 + 월 운영비, 손익분기 봉쇄율 33%
            → 15장의 계산

8. 다음     성공 시 인텐트 3개로 확대 → 이후 아웃바운드 검토
```

6번을 빼먹는 제안서가 많습니다. **리스크를 먼저 꺼내는 쪽이 더 신뢰받습니다.**
상대는 어차피 그 걱정을 하고 있고, 우리가 먼저 말하면 "이미 알고 대비했다"로
읽힙니다. 감추면 나중에 발견됐을 때 신뢰가 무너집니다.

## 파일럿 후에 벌어지는 일

성공해도 바로 확대되지 않습니다. 대개 이런 질문들이 나옵니다.

- 통화량이 10배가 되면 견디는가 (부하)
- 우리 CRM과 연동되는가 (통합)
- 통화 데이터는 어디에 저장되는가 (보안·컴플라이언스)
- 담당자가 프롬프트를 직접 고칠 수 있는가 (운영권)
- 벤더가 망하면 어떻게 되는가 (지속성)

마지막 두 개가 특히 자주 나옵니다. **고객사는 통제권을 원합니다.** 모든 변경을
우리에게 요청해야 하는 구조는 확대 단계에서 막힙니다.

그래서 파일럿 단계부터 **고객이 직접 만질 수 있는 부분**을 만들어두는 게 좋습니다.
프롬프트 편집 화면, 봉쇄율 대시보드, 이관 조건 설정 같은 것들입니다. 기술적으로는
사소하지만 도입 결정에 크게 기여합니다.

## 남는 질문

이 책은 "전화를 받아 대화하고 일을 처리하는 AI"를 다뤘습니다. 지금 시점에서
이건 대체로 사람 상담원을 흉내 내는 방향입니다.

그런데 정말 흉내 내는 게 목표일까요.

기계는 사람이 못 하는 걸 할 수 있습니다. 동시에 천 통을 받고, 절대 지치지 않고,
모든 통화 기록을 즉시 검색합니다. 반대로 사람이 쉽게 하는 걸 못 합니다. 화난
고객을 달래고, 규정 밖의 예외를 판단하고, 말하지 않은 것을 알아챕니다.

**"사람처럼"이 아니라 "사람과 다르게 잘하는 것"이 무엇인지**를 찾는 쪽에 아직
열려 있는 공간이 많아 보입니다. IVR을 대체하는 것에서 시작했지만, 거기서 끝날
이유는 없습니다.

---

**한 문장 요약**
파일럿의 목적은 성능 자랑이 아니라 "실패해도 안전하다"를 설계로 보여주는 것이고,
그래서 범위는 좁게, 기간은 짧게, 비교군과 롤백 스위치를 반드시 둔다.
