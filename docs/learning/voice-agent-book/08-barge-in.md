# 08. 끼어들기의 해부

## 대화와 자동응답기를 가르는 것

봇이 말하는 도중에 사용자가 말을 시작합니다. 봇이 계속 떠들면 그 순간 사용자는
확신합니다. "아, 이거 녹음이구나."

끼어들기 처리 — **barge-in** — 는 기능 하나가 아니라 "이게 대화인가 아닌가"를
결정하는 경계선입니다. 그리고 구현이 생각보다 훨씬 까다롭습니다.

## 순진한 해법

```
사용자 음성이 감지되면 → TTS 재생을 멈춘다
```

한 줄이면 될 것 같습니다. 실제로 이렇게 구현하면 대부분 동작하는 것처럼 보입니다.
그리고 네 가지 방식으로 미묘하게 틀립니다.

## 깨지는 방식 넷

### 하나. 멈췄는데 계속 말한다

가장 자주 나오는 버그입니다. 끼어들었는데 봇이 1~2초 더 말합니다.

원인은 **오디오가 이미 나가 있기 때문**입니다.

```
TTS 생성 ──▶ 전송 큐 ──▶ 네트워크 ──▶ 상대방 버퍼 ──▶ 스피커
   ↑ 여기만 멈춤        └────── 이미 나간 소리는 계속 재생 ──────┘
```

생성을 멈춰도 이미 전송된 오디오는 상대방 쪽 버퍼에 쌓여 있습니다. 6장에서 본
지터 버퍼가 여기서는 방해가 됩니다. 지연을 흡수하려고 쌓아둔 것이 취소를 늦춥니다.

그래서 **"이미 보낸 것을 버려라"는 신호를 별도로 보내야 합니다.** 전화 서비스들이
제공하는 버퍼 비우기 명령이 정확히 이 용도입니다. 이 신호를 안 보내면 아무리
빨리 멈춰도 사용자에게는 봇이 계속 말하는 것으로 들립니다.

### 둘. 다음 턴에 이전 응답이 섞인다

TTS만 멈추고 LLM 스트림을 그대로 두면, 백그라운드에서 계속 토큰이 생성됩니다.
그리고 다음 턴에 그 찌꺼기가 섞여 나옵니다.

끼어들기가 발생하면 **LLM 요청도 함께 취소해야** 합니다. 진행 중인 도구 호출이
있다면 그것도 어떻게 할지 정해야 합니다. 조회는 버려도 되지만, 이미 나간 쓰기
요청은 취소할 수 없습니다. 12장에서 다룰 문제입니다.

### 셋. 봇이 안 한 말을 했다고 믿는다

가장 교묘하고, 가장 자주 빠뜨립니다.

봇이 세 문장을 생성했는데 첫 문장 재생 중에 끼어들었다고 합시다. 대화 기록에는
무엇을 남겨야 할까요.

```
생성된 것:  "네, 확인해 보니 8월 3일 저녁 7시로 예약되어 있습니다.
             변경을 원하시면 새 날짜를 말씀해 주세요.
             참고로 취소 수수료는 없습니다."

실제 재생:  "네, 확인해 보니 8월 3일 저녁—"
```

생성된 전체를 기록에 남기면, 봇은 자기가 취소 수수료 얘기를 했다고 믿습니다.
사용자가 "수수료 있어요?"라고 물으면 "아까 말씀드렸듯이 없습니다"라고 답합니다.
사용자는 들은 적이 없습니다.

**실제로 재생된 부분까지만** 대화 기록에 남겨야 합니다.

```
기록: "네, 확인해 보니 8월 3일 저녁 (사용자가 끼어듦)"
```

어디까지 재생됐는지 알려면 재생 진행 상황을 추적하는 장치가 필요합니다. 전화
서비스들이 제공하는 재생 완료 표시(mark) 이벤트가 이 용도로 쓰입니다.

### 넷. 자기 목소리에 끼어든다

봇이 말하는 중에 스피커 소리가 마이크로 되돌아옵니다. 시스템은 이걸 사용자 발화로
오인하고 스스로 끼어들기를 발동합니다. 그리고 자기 말을 STT로 인식해서 엉뚱한
응답을 만듭니다.

**에코**입니다. 세 가지 층위에서 대응합니다.

| 대응 | 방식 | 한계 |
|---|---|---|
| **음향 에코 제거(AEC)** | 출력 신호를 알고 있으니 입력에서 빼냄 | 브라우저는 내장, 전화망은 상황에 따라 다름 |
| **텍스트 대조** | 방금 말한 문장과 인식 결과가 비슷하면 무시 | 사후 처리라 이미 반응했을 수 있음 |
| **하프 듀플렉스** | 말하는 동안 마이크를 닫음 | **끼어들기를 포기하는 것** — 최후 수단 |

세 번째는 문제를 푸는 게 아니라 회피하는 것입니다. 그래도 에코가 잡히지 않는
환경에서는 어색한 대화보다 낫다고 판단할 수 있습니다.

## 어디까지가 끼어들기인가

여기서 새로운 문제가 생깁니다. 사용자가 내는 모든 소리에 반응하면 안 됩니다.

```
"음"        ← 맞장구, 끼어들기 아님
"네네"      ← 듣고 있다는 신호, 끼어들기 아님
"아 그게"   ← 진짜 끼어들기
기침, 문 닫는 소리  ← 사람 목소리도 아님
```

언어학에서 **backchannel**이라고 부르는 맞장구는 "계속 말해"라는 뜻이지 "멈춰"가
아닙니다. 여기에 반응해 봇이 멈추면 대화가 계속 끊깁니다.

구분 방법은 완벽하지 않지만 몇 가지 단서가 있습니다.

- **길이** — 300ms 이하의 짧은 발성은 맞장구일 가능성이 높음
- **내용** — "네", "음", "아" 같은 어휘 목록과 대조
- **에너지** — 맞장구는 대개 작은 소리

실무에서는 **짧은 지연을 두고 판단**합니다. 소리가 감지되면 즉시 멈추지 않고
200~300ms 지켜본 뒤, 계속 이어지면 진짜 끼어들기로 처리합니다. 반응이 조금
느려지지만 오작동이 크게 줍니다.

## 정리: 끼어들기가 발생하면 해야 할 일

```
1. TTS 생성 중단
2. 이미 전송된 오디오 버퍼 폐기       ← 가장 자주 빠뜨림
3. LLM 스트림 취소
4. 실제 재생된 부분까지만 기록에 반영   ← 두 번째로 자주 빠뜨림
```

네 가지 중 하나라도 빠지면 증상이 다르게 나타납니다.

| 빠뜨린 것 | 증상 |
|---|---|
| 1 | 비용만 낭비, 눈에 안 보임 |
| 2 | **끼어들었는데 봇이 계속 말함** |
| 3 | 다음 턴에 이전 응답이 섞임 |
| 4 | 봇이 안 한 말을 했다고 주장함 |

## 남는 질문

지금까지는 "사용자가 끼어들면 봇이 멈춘다"만 다뤘습니다. 반대 방향은 어떨까요.
**봇이 사용자에게 끼어들어야 할 때**도 있습니다.

사용자가 5분째 상황을 설명하고 있는데 봇이 이미 필요한 정보를 다 얻었다면요.
또는 사용자가 잘못된 전제로 말하고 있어서 빨리 바로잡아야 한다면요.

사람은 이럴 때 자연스럽게 끼어듭니다. 하지만 봇이 끼어들면 무례하게 느껴집니다.
같은 행동인데 주체가 기계라는 이유로 다르게 받아들여집니다. 기술 문제가 아니라
사회적 기대의 문제이고, 아직 좋은 답이 없습니다.

**한 문장 요약**
끼어들기 처리는 TTS를 멈추는 것 하나가 아니라 네 가지 일이고, 그중 "이미 전송된
오디오 폐기"와 "실제 재생된 부분만 기록"이 가장 자주 누락된다.
