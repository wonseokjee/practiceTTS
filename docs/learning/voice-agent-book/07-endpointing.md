# 07. 말이 끝났다는 것을 어떻게 아는가

## 대답하려면 먼저 끝난 줄 알아야 한다

이 판단 하나가 음성 에이전트의 대화 품질을 절반쯤 결정합니다. 그런데 놀랍도록
어렵습니다.

문제를 정확히 정의해봅시다. 마이크에서 오디오가 계속 들어옵니다. 어느 시점에
"이제 사용자의 발화가 끝났다"고 선언하고 응답 생성을 시작해야 할까요.

너무 일찍 선언하면 사용자 말을 끊습니다. 너무 늦게 선언하면 어색한 침묵이
생깁니다. 그리고 이 판단에 쓰는 시간은 그대로 지연 예산에서 빠져나갑니다.

## 순진한 해법: 침묵을 센다

```
소리가 없는 상태가 500ms 지속되면 → 발화 끝
```

이걸 **VAD**(Voice Activity Detection)라고 합니다. 소리가 사람 목소리인지
배경 소음인지 판별하는 것까지 포함해서요. Silero VAD 같은 작은 모델이 이 일을
잘 해냅니다. 연산이 가벼워서 실시간으로 돌릴 수 있습니다.

구현이 간단하고, 대부분의 경우에 잘 동작합니다. 그리고 나머지 경우에 참담하게
실패합니다.

## 어떻게 깨지는가

실제 통화에서 이 방식이 무너지는 상황들입니다.

### 생각하느라 쉰 것을 끝난 걸로 오해

```
사용자: "다음 주 화요일에... (700ms 침묵) ...네 명이요"
             ↑ 여기서 봇이 끼어들어 "화요일에 몇 분이신가요?"
```

말을 끊긴 사용자는 짜증이 납니다. 그리고 다시 말하는 동안 봇도 말하고 있어서
서로 겹칩니다.

### 숫자를 읽는 중간에 끊김

```
사용자: "제 번호는 공일공 (400ms) 일이삼사 (500ms) 오육칠팔"
                              ↑ 여기서 종료 판정
```

전화번호나 예약번호를 부를 때 사람은 자연스럽게 끊어 읽습니다. 그 간격이 침묵
임계값을 넘습니다. 하필 가장 중요한 정보를 받는 순간에 실패합니다.

### 짧은 대답에서 시간 낭비

```
사용자: "네."
        └─ 500ms 대기 ─┘  ← 이미 끝난 게 명백한데 기다림
```

"네", "아니요" 같은 명백한 종결에서도 똑같이 500ms를 기다립니다. 대화가 리듬을
잃습니다.

### 정정을 놓침

```
사용자: "화요일로 해주세요 (600ms) 아 아니다 수요일이요"
                            ↑ 여기서 이미 화요일로 처리 시작
```

앞부분만 듣고 처리를 시작했는데 뒤에서 뒤집힙니다. 이미 API를 호출했다면 되돌려야
합니다.

**공통 원인**은 하나입니다. **침묵의 길이만으로는 발화가 끝났는지 알 수 없습니다.**
사람은 침묵의 길이로 판단하지 않습니다. 말이 의미적으로 완결되었는지를 봅니다.

## 그래서 실제로는: 의미를 함께 본다

**Semantic endpointing**이라고 부릅니다. 침묵 길이와 **문장의 완결성**을 함께
판단합니다.

```
"다음 주 화요일에"          → 미완결 → 더 기다린다 (임계값 1200ms로 연장)
"다음 주 화요일에 네 명이요" → 완결   → 즉시 종료 (300ms면 충분)
"네"                        → 완결   → 즉시 종료 (200ms)
```

같은 500ms 침묵이라도 앞 문장이 무엇이냐에 따라 다르게 처리합니다.

구현 방식은 크게 두 갈래입니다.

### 작은 모델로 분류

부분 인식 결과를 받아 "이 문장이 완결되었는가"를 이진 분류하는 작은 모델을 둡니다.
전용 turn-detection 모델을 쓰기도 하고, 가벼운 LLM에 물어보기도 합니다.

정확하지만 **추론 시간이 지연에 더해집니다.** 50~100ms 정도인데, 800ms 예산에서
적지 않은 비중입니다. 얻는 정확도가 그 비용보다 큰지 따져봐야 합니다.

### 언어 규칙으로 임계값 조절

문장이 어떻게 끝났는지 보고 침묵 임계값을 동적으로 바꿉니다.

한국어는 여기서 유리한 면이 있습니다. 어미가 문장의 완결 여부를 비교적 명확하게
드러내기 때문입니다.

```
조사·연결어미로 끝남  ("~에", "~하고", "~인데")  → 임계값 늘림
종결어미로 끝남      ("~요", "~습니다", "~죠")   → 임계값 줄임
```

규칙 기반인데도 꽤 잘 동작합니다. 추론 비용이 0이라는 점이 큰 장점입니다.

## 한국어의 함정

다만 한국어에는 이 방식을 배신하는 패턴이 많습니다.

```
"예약하려고 하는데요"     ← 종결어미인데 말이 안 끝남
"화요일 저녁이 좋을 것 같고요"  ← 종결어미인데 이어짐
"네 그러니까 제가요"      ← "요"로 끝나지만 계속됨
```

한국어 구어체는 종결어미를 붙이면서 말을 이어가는 습관이 강합니다. 그래서
영어 기준으로 학습된 endpointing 모델이 한국어에서 유독 잘 안 맞습니다.
영어는 문장 끝에서 억양이 내려가고 구조적으로도 완결이 명확한 편인데,
한국어는 그렇지 않습니다.

**한국어 음성 에이전트를 만든다면 이 부분은 직접 튜닝해야 합니다.** 기성 솔루션이
그대로 통하지 않는, 몇 안 되는 진짜 로컬 문제 중 하나입니다.

## 예측이라는 다른 길

1장에서 사람은 상대의 말이 끝나기 전에 예측한다고 했습니다. 기계도 그럴 수
있을까요.

부분적으로 가능합니다. **부분 인식 결과가 안정되면 최종 확정을 기다리지 않고
응답 생성을 미리 시작하는** 방식입니다. 최종 결과가 예상과 같으면 이미 만들어둔
응답을 그대로 쓰고, 다르면 버립니다.

```
t=0.0s  "다음 주 화..."          
t=0.4s  "다음 주 화요일"          → 여기서 투기적으로 LLM 시작
t=0.8s  "다음 주 화요일 네 명"     → 예측 빗나감, 폐기하고 재시작
t=1.1s  종료 판정                 → 최종 결과로 다시 시작
```

버려지는 계산과 토큰이 생기지만, 맞았을 때 아끼는 300~400ms가 훨씬 값집니다.
어차피 LLM 호출 비용은 통화 원가에서 큰 비중이 아닙니다(15장 참조).

## 남는 질문

지금까지의 모든 방식은 **오디오와 텍스트만** 봅니다. 그런데 사람은 억양도 씁니다.
문장 끝에서 음높이가 내려가면 끝, 유지되면 계속 — 이 신호가 실제로 강력합니다.

운율(prosody)을 함께 보는 종단 감지는 활발히 연구되고 있지만 아직 널리 쓰이지는
않습니다. 그리고 8kHz 전화 오디오에서 운율 정보가 얼마나 살아남을지도 별도의
문제입니다.

그리고 더 근본적인 질문. 애초에 "발화가 끝났다"는 판정이 필요 없다면 어떨까요.
사용자가 말하는 동안 계속 응답을 준비하고, 끊기면 그 시점의 최선을 내놓는 구조라면.
Speech-to-speech 모델이 지향하는 방향이고, 10장에서 다룹니다.
