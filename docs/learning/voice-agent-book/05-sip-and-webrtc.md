# 05. 같은 문제, 두 개의 답

## 통화를 연결한다는 것

A가 B에게 전화를 건다고 할 때, 실제로 해결해야 하는 문제는 생각보다 많습니다.

1. B가 어디 있는지 어떻게 찾는가
2. B가 받을 수 있는 상태인지 어떻게 아는가
3. 어떤 코덱으로 주고받을지 어떻게 합의하는가
4. 실제 음성 데이터는 어느 경로로 흐르는가
5. 누가 먼저 끊었는지 어떻게 아는가

SIP과 WebRTC는 서로 다른 시대에 서로 다른 목적으로 만들어졌지만, 이 문제들에
**놀랍도록 비슷한 방식으로** 답했습니다. 그 공통점을 먼저 보는 것이 둘 다
이해하는 지름길입니다.

## 공통 통찰: 시그널링과 미디어는 다른 문제다

두 프로토콜의 가장 중요한 공통점입니다.

```
        ┌──── 시그널링: 누구와, 어떻게 연결할지 협상 ────┐
     A                                                  B
        └──── 미디어: 실제 음성 데이터 (RTP) ───────────┘
```

**연결을 협상하는 경로와 음성이 흐르는 경로가 다릅니다.**

왜 나눴을까요. 협상은 가끔 일어나고 신뢰성이 중요합니다. 반면 음성은 초당 50번씩
쏟아지고 신뢰성보다 속도가 중요합니다. 하나가 다 하려고 하면 둘 다 못 합니다.

이 분리를 이해하면 뒤따르는 많은 것들이 자연스러워집니다. "SIP 연결은 됐는데
소리가 안 들려요"라는 흔한 증상도 그렇습니다. 시그널링은 성공했지만 미디어
경로가 막힌 것이고, 둘은 별개의 문제입니다.

## SIP — 전화망의 방식

1990년대에 만들어졌고, HTTP를 닮았습니다. 텍스트 기반 요청/응답 구조입니다.

```
발신자                          수신자
  │──────── INVITE ───────────▶│   "통화합시다" (내 코덱 목록 동봉)
  │◀─────── 100 Trying ────────│   "요청 받았어요"
  │◀─────── 180 Ringing ───────│   "벨 울리는 중"
  │◀─────── 200 OK ────────────│   "받았습니다" (합의된 코덱 동봉)
  │──────── ACK ──────────────▶│   "확인"
  │                            │
  │══════ RTP 음성 데이터 ═════▶│   ← 여기는 SIP이 아님
  │                            │
  │──────── BYE ──────────────▶│   "끊습니다"
  │◀─────── 200 OK ────────────│
```

응답 코드가 HTTP와 같은 체계입니다. 1xx는 진행 중, 2xx는 성공, 4xx는 실패.
`486 Busy Here`는 통화 중, `404 Not Found`는 없는 번호입니다. HTTP를 아는
사람이라면 절반은 이미 아는 셈입니다.

INVITE 안에 실려 가는 코덱 협상 정보를 **SDP**(Session Description Protocol)라고
합니다. "나는 G.711과 Opus를 지원하고, 내 미디어는 이 IP의 이 포트로 보내라"는
내용이 담깁니다. 상대가 200 OK로 자기 SDP를 돌려주면 협상이 끝납니다.

## WebRTC — 브라우저의 방식

2010년대에 만들어졌고, 목표가 달랐습니다. **브라우저에서 플러그인 없이 실시간
통신**을 하는 것.

여기서 SIP과 결정적으로 다른 선택이 나옵니다. **WebRTC 표준은 시그널링을 정의하지
않습니다.**

```
WebRTC가 정하는 것:   미디어 전송, 코덱, 암호화, NAT 통과
WebRTC가 안 정하는 것: SDP를 어떻게 주고받을지  ← 개발자가 알아서
```

처음 배울 때 가장 헷갈리는 지점이고, "WebRTC가 연결이 안 돼요" 문제의 절반이
여기서 나옵니다. WebSocket이든 HTTP 폴링이든 비둘기든, SDP를 상대에게 전달할
방법은 직접 만들어야 합니다.

왜 이렇게 했을까요. 웹에는 이미 서버와 통신할 방법이 많았고, 각 서비스마다
사용자 인증과 상대 찾기 방식이 다릅니다. 표준이 하나로 강제하면 오히려 방해가
됩니다. 필요한 것만 정하고 나머지는 열어둔 설계입니다.

## NAT라는 골칫거리

WebRTC가 SIP보다 훨씬 공을 들인 부분입니다.

대부분의 기기는 공유기 뒤에 있어서 사설 IP를 씁니다. 내 IP가 `192.168.0.5`라고
상대에게 알려줘도 상대는 거기로 접속할 수 없습니다. 그 주소는 전 세계에 수억 개
있으니까요.

세 가지 도구가 이 문제를 다룹니다.

| | 역할 | 비용 |
|---|---|---|
| **STUN** | "밖에서 본 내 주소가 뭐야?"를 알려주는 서버 | 거의 공짜 (질의 한 번) |
| **TURN** | 직결이 안 되면 미디어를 대신 중계 | 비쌈 (모든 트래픽이 통과) |
| **ICE** | 여러 후보 경로를 실제로 시도해보고 되는 걸 고름 | — |

ICE의 작동 방식이 재미있습니다. 이론적으로 어느 경로가 될지 따지는 대신,
**가능한 모든 후보를 동시에 시도해보고 먼저 통하는 걸 씁니다.** 네트워크 환경이
너무 다양해서 예측보다 실측이 낫다는 판단입니다.

여기서 실무 함정이 하나 나옵니다. 개발 중에는 STUN만으로 잘 됩니다. 개발자
네트워크는 대체로 관대하니까요. 그러다 기업 방화벽 뒤 사용자에게서 갑자기
실패합니다. UDP가 막혀 있거나 Symmetric NAT인 환경에서는 TURN이 필수입니다.

**"프로덕션에 TURN 서버를 준비했는가"** — 실전 경험을 가르는 질문입니다.

## 둘을 나란히 놓고 보면

| | SIP | WebRTC |
|---|---|---|
| 만들어진 때 | 1990년대 | 2010년대 |
| 시그널링 | 프로토콜이 정의함 | **개발자가 구현** |
| 미디어 | RTP | SRTP (암호화 강제) |
| 기본 코덱 | G.711 | Opus |
| NAT 통과 | 취약 (별도 장비 필요) | ICE/STUN/TURN 내장 |
| 암호화 | 선택 | **필수** |
| 주소 체계 | 전화번호, SIP URI | 서비스가 정함 |

암호화가 SIP에서는 선택이고 WebRTC에서는 필수인 점이 두 프로토콜의 시대 차이를
잘 보여줍니다.

## 음성 AI는 어디에 서 있는가

브라우저 사용자와 전화 사용자를 모두 받으려면 양쪽에 다 발을 걸쳐야 합니다.

```
브라우저 ──WebRTC──┐
                   ├──▶ 음성 AI 에이전트
전화     ──SIP─────┘
```

이 중간 지점에 서는 구성요소를 **B2BUA**(Back-to-Back User Agent)라고 부릅니다.
양쪽 호를 각각 종단하면서 중계하는 구조인데, 음성 AI 에이전트가 정확히 여기에
해당합니다. 사용자 입장에서는 에이전트가 통화 상대이고, 시스템 입장에서는
에이전트가 두 개의 세션을 각각 관리합니다.

실무에서는 이 계층을 직접 구현하지 않습니다. Twilio나 LiveKit 같은 서비스가
SIP↔WebRTC 변환을 대신 해주고, 우리는 오디오 스트림만 받아 처리합니다. 다만
문제가 생겼을 때 어느 계층에서 깨졌는지 판단하려면 구조를 알고 있어야 합니다.

## 남는 질문

두 프로토콜이 시그널링과 미디어를 나눈 건 합리적이었습니다. 그런데 이 분리는
**디버깅을 어렵게 만듭니다.** 통화가 안 되는데 원인이 시그널링인지 미디어인지,
어느 홉에서 막혔는지 알기 어렵습니다.

그래서 이 분야에서는 패킷 캡처가 여전히 기본 기술입니다. Wireshark로 SIP 흐름을
따라가는 능력은 대체재가 없습니다. 로그만으로는 보이지 않는 것들이 있습니다.

---

**한 문장 요약**
SIP과 WebRTC 모두 시그널링과 미디어를 분리했고, 차이는 SIP이 시그널링까지
정의한 반면 WebRTC는 미디어와 NAT 통과만 정의하고 시그널링은 개발자에게 남겼다는 점이다.
