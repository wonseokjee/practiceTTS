# 13. 보이지 않는 것은 고칠 수 없다

## 통화는 증발한다

서버 애플리케이션이 이상하면 로그를 봅니다. 요청, 응답, 스택 트레이스가 남아
있으니 재구성할 수 있습니다.

통화는 그렇지 않습니다. 사용자가 "봇이 이상했어요"라고 신고했을 때, 무엇이
이상했는지 알 방법이 기본적으로 없습니다. 소리는 사라졌고, 그 순간의 판단 과정도
사라졌습니다.

그래서 음성 에이전트는 **처음부터 관측 가능하게 만들어야** 합니다. 나중에 붙이는
게 아니라 처음부터입니다.

## 무엇을 기록해야 하는가

일반적인 로깅으로는 부족합니다. 통화 한 건을 재구성하려면 세 층이 필요합니다.

```
1층. 무슨 일이 있었나   전사, 도구 호출, 응답
2층. 얼마나 걸렸나      구간별 시간
3층. 왜 그랬나          모델에 들어간 프롬프트, 나온 토큰
```

세 층이 **같은 통화 ID로 묶여 있어야** 의미가 있습니다. 따로 놀면 대조가 불가능합니다.

## 구조: 통화가 곧 하나의 추적 단위

관측성 도구들은 대체로 이런 구조를 씁니다.

```
Trace  = 통화 한 건
 ├─ Span "턴 1"
 │   ├─ Span  종단 감지        210ms
 │   ├─ Span  STT              95ms
 │   ├─ Span  LLM 호출        380ms  (토큰 수, 비용 자동 기록)
 │   └─ Span  TTS 첫 바이트   140ms
 ├─ Span "턴 2"
 └─ Span "도구: 예약조회"      620ms
```

**통화 한 건을 하나의 trace로 잡는 것**이 핵심 결정입니다. 이렇게 하면 "그 통화"를
클릭 한 번으로 전체 재생할 수 있습니다. 턴별로 따로 기록하면 통화 단위 분석이
불가능해집니다.

9장의 지연 예산이 여기서 검증됩니다. 예산표의 각 항목이 span 하나에 대응하도록
설계하면, 대시보드가 곧 예산 대비 실적표가 됩니다.

## 평균은 거짓말을 한다

9장에서 짧게 언급한 것을 여기서 제대로 다룹니다.

```
p50 (중앙값)  720ms
p95           1,850ms
p99           4,200ms
```

p50만 보면 훌륭한 시스템입니다. 그런데 통화 한 건에 턴이 열 번이라면?

한 턴이 p95에 걸릴 확률이 5%이므로, 열 턴 중 **최소 한 번 걸릴 확률은 약 40%**
입니다. 통화 열 건 중 네 건에서 사용자가 어색한 침묵을 경험합니다.

사용자는 평균을 기억하지 않습니다. **이상했던 순간을 기억합니다.** 그래서 음성에서는
p95, 가능하면 p99를 봐야 합니다.

## 조용한 실패를 어떻게 잡는가

12장 끝에서 던진 질문입니다. 에러도 안 나고 모든 게 정상으로 보이는데 결과가
틀린 경우.

로그만으로는 못 잡습니다. 별도의 신호가 필요합니다.

| 신호 | 무엇을 의심하게 하는가 |
|---|---|
| 되묻기 횟수 급증 | STT 정확도 저하 (네트워크? 모델 변경?) |
| 특정 턴에서 이탈 급증 | 그 지점의 응답에 문제 |
| 통화 길이 분포 변화 | 봇이 루프에 빠지거나 조기 종료 |
| 도구 호출 없이 끝난 비율 증가 | 모델이 도구를 안 부르기 시작 |
| 상담원 이관율 상승 | 봇 성능 저하 |

마지막 두 개가 특히 유용합니다. **도구 호출률**은 조용한 실패를 잡는 좋은 지표입니다.
프롬프트를 수정했더니 모델이 도구를 덜 부르게 되는 일이 실제로 자주 일어나고,
에러 로그에는 아무것도 안 남습니다.

## 프롬프트를 바꿨는데 나아졌는지 어떻게 아는가

음성 에이전트에서 가장 흔한 실패 패턴입니다. 프롬프트 한 줄을 고치고, 몇 번
통화해보고, "괜찮은 것 같네" 하고 배포합니다. 그리고 다른 데가 망가진 걸 일주일 뒤에 압니다.

필요한 건 **골든셋과 자동 채점**입니다.

```
골든셋: 시나리오 40건 (정상 / 말 끊김 / 잡음 / 사투리 / 악의적 입력)
        각각 기대 결과 명시

배포 전: 40건 자동 실행 → 점수 → 기준 미달이면 배포 중단
```

여기서 음성 특유의 어려움이 있습니다. **텍스트 입력으로는 테스트가 안 됩니다.**
7장의 종단 감지, 8장의 끼어들기는 실제 오디오 타이밍이 있어야 재현됩니다.

그래서 **합성 발화를 실시간 속도로 주입**하는 방식을 씁니다. 미리 녹음한 오디오
파일을 20ms 프레임 단위로, 실제 재생 속도에 맞춰 파이프라인에 밀어 넣습니다.

한꺼번에 밀어 넣으면 안 됩니다. VAD와 종단 감지가 전혀 다르게 동작해서 테스트가
무의미해집니다. 실시간 속도를 지키는 게 핵심입니다.

## 채점은 무엇으로 하는가

두 종류가 필요합니다.

**정답이 명확한 것** — 규칙으로 채점

```
추출된 날짜 == 기대 날짜 ?
상담원 이관 여부 == 기대값 ?
턴 지연 p95 < 1200ms ?
```

**정답이 명확하지 않은 것** — 모델로 채점

```
"아래 응답을 평가하세요.
 - 두 문장 이내인가?
 - 한 번에 하나만 물어봤는가?
 - 처리 불가한 요청에 상담원 연결을 제안했는가?
 0~1 점수와 근거를 함께 출력하세요."
```

두 번째를 LLM-as-a-judge라고 부릅니다. 완벽하진 않지만, 사람이 매번 40건을 듣는
것보다 훨씬 지속 가능합니다. **채점자가 흔들리지 않도록 기준을 구체적으로 쓰는
것**이 관건입니다. "자연스러운가"는 나쁜 기준이고, "두 문장 이내인가"는 좋은 기준입니다.

## 비용도 관측 대상이다

통화당 원가를 알아야 15장의 계산이 가능합니다. 그런데 이걸 사후에 청구서로
알아내려고 하면 통화 단위로 쪼갤 수가 없습니다.

trace에 처음부터 비용을 기록해야 합니다. 대부분의 관측성 도구가 LLM 호출의
토큰 수와 비용을 자동으로 잡아주므로, 나머지(STT, TTS, 텔레포니)만 직접 붙이면
됩니다.

```
통화 CA123 총원가: $0.19
  LLM   $0.076
  STT   $0.030
  TTS   $0.045
  회선  $0.039
```

이 숫자가 있어야 "봉쇄율 몇 %부터 남는 장사인가"를 계산할 수 있습니다.

## 남는 질문

관측성을 갖추면 문제를 볼 수 있게 됩니다. 그런데 통화 내용은 민감정보입니다.
전사와 오디오를 다 저장하면 그 자체가 위험 자산이 됩니다.

여기서 긴장이 생깁니다. **디버깅하려면 봐야 하고, 보호하려면 안 봐야 합니다.**

실무적 절충은 대개 이렇습니다. 마스킹된 전사는 오래 보관하고, 원본 오디오는
짧게만 보관하고, 접근에는 별도 권한을 둡니다. 그리고 이 정책은 기술이 아니라
법무가 정합니다.

이 지점부터는 엔지니어링 문제가 아니라 사업 문제입니다. 5부의 주제입니다.

---

**한 문장 요약**
통화는 증발하므로 처음부터 관측 가능하게 설계해야 하고, 평균이 아니라 p95를 보며,
프롬프트 변경의 효과는 감이 아니라 골든셋 점수로 확인해야 한다.
